Implementation Plan — Manual QA Excel Test-Case Suite

Feature slug: qa-test-case-suite · Nguồn: guide/functional-overview.vi.html (28 chức năng, 4 nhóm vai trò) + planning/master-plan.html (37 edge case E01–E20 / M01–M12 / A01–A07, đã có test tự động TestEdge_*). Đây là bộ checklist thủ công song song với bộ test tự động đã có — không thay thế, không trùng lặp phạm vi.

⛔ Phạm vi của lượt làm việc này chỉ dừng ở 2 tài liệu plan. Không tạo file .xlsx nào, không thực thi test case nào, không viết code nào trong lượt này. Người dùng yêu cầu rõ: "tôi duyệt xong mới được phép làm" — hai tài liệu này (implementation-plan.html + solution-architecture.html) là toàn bộ output, chờ review trước khi sang giai đoạn tạo file Excel thật.

2. Scope & Non-goals

Ships (trong 2 tài liệu plan này)

  • Vị trí + cấu trúc thư mục cho bộ file Excel (chưa tạo file, chỉ định vị trí + đặt tên).
  • Schema cột chi tiết, áp dụng thống nhất cho cả 5 file.
  • Quy ước đặt Test ID, traceable ngược về cả feature (functional-overview) và edge-case ID (E/M/A).
  • Ước lượng số lượng test case theo từng chức năng (bảng task breakdown thật, không phải "tuỳ").
  • Mô hình thực thi: Claude sẽ chạy từng nhóm case bằng công cụ gì ở giai đoạn sau, phân loại rõ AUTO-API / AUTO-WEB / PARTIAL / HUMAN.

Non-goals (rõ ràng loại trừ khỏi lượt này)

  • Không thiết kế framework test tự động — đó là nỗ lực song song, khác người, khác artifact (đã có TestEdge_* + skill gen-api-test lo phần đó).
  • Không tạo bất kỳ file .xlsx nào trong lượt này.
  • Không chạy thử bất kỳ test case nào, kể cả để "xem có work không" — kể cả khi có vẻ hữu ích.
  • Không viết script sinh Excel (openpyxl/xlsxwriter...) — đó là việc của giai đoạn triển khai sau khi duyệt.

3. Vị trí & cấu trúc thư mục

Vị trí đề xuất: D:\hpay\hpay-docs\qa\test-cases\ cho các file .xlsx thật (giai đoạn sau), và D:\hpay\hpay-docs\qa\plan\ cho 2 tài liệu plan này. Lý do chọn hpay-docs thay vì một trong 3 repo code:

  • Bộ test case này không thuộc về 1 repo — mỗi file thường có cả bước ở mobile, backend, và đôi khi admin trong cùng một kịch bản nghiệp vụ (vd. checker duyệt lệnh chi cần cả mobile app của checker lẫn API backend).
  • hpay-docs đã là nơi giữ "thiết kế tổng" và tài liệu liên-repo (xem planning/master-plan.html, guide/functional-overview.vi.html) — bộ QA checklist là một tài liệu vận hành liên-repo cùng bản chất, không phải kế hoạch triển khai code của riêng 1 repo.
  • QA/tester không cần checkout cả 3 repo code để tìm file test case — 1 chỗ duy nhất, đúng tinh thần hpay-docs là "index" cho toàn hệ thống.

Vì sao tách sheet 05 riêng thay vì nhét hết edge case vào cột "Related Edge ID" của sheet 01–04? Cả hai đều làm — không loại trừ nhau. Sheet 01–04 vẫn có ít nhất 1 case tham chiếu edge ID ngay tại chức năng liên quan (vd. case "Chuyển P2P — double-tap" trong sheet 01 có cột Related Edge ID = M01). Nhưng nhiều edge case (đặc biệt E02/E03/E08/E20 — race condition, deadlock, lease claim) đòi hỏi dàn dựng nhiều actor cùng lúc / nhiều bước song song mà 1 dòng Excel bình thường không diễn tả nổi rõ ràng — sheet 05 dành riêng 1 dòng/ID với cột Steps đủ dài để mô tả kịch bản đa-actor, và đóng vai trò "bảng tổng kiểm" để không sót ID nào trong 37 ID đã cam kết ở master-plan.html mục 5 (Definition of Done).

5. Quy ước đặt Test ID

TC-<GROUP>-<NNN>          # sheet 01-04, đánh số tuần tự trong nhóm
TC-EDG-<EDGE-ID>          # sheet 05, ID = chính edge-case ID gốc

GROUP ∈ { PER, BIZ, ADM, PLT }
  PER = 01-personal-user
  BIZ = 02-business-maker-checker
  ADM = 03-admin-ops
  PLT = 04-platform-crosscutting

Ví dụ:
  TC-PER-001   → sheet 01, case #1 (thường là happy path Đăng ký)
  TC-PER-014   → sheet 01, case liên quan double-tap khi chuyển P2P
  TC-BIZ-022   → sheet 02, case Checker ký OTP
  TC-EDG-E08   → sheet 05, kiểm chứng thủ công song song với TestEdge_E08_CheckerRaceSingleFinalize
  TC-EDG-M01   → sheet 05, kiểm chứng thủ công song song với TestEdge_M01_DoubleTapTransfer_SingleRequest
  TC-EDG-A01   → sheet 05, kiểm chứng thủ công 409 ERR_ALREADY_FINALIZED giữa 2 admin review

Traceability 2 chiều: mỗi case chức năng (01–04) khi chạm tới 1 rủi ro đã có edge-ID ghi đúng ID đó vào cột J — Related Edge ID (không tạo TC-EDG mới trùng); ngược lại, mọi ID trong 37 ID gốc đều có đúng 1 dòng "chốt" trong sheet 05 dù đã được nhắc ở sheet nào khác. Không có ID nào bị bỏ sót — đối chiếu được bằng cách lọc cột J qua cả 5 file rồi so với danh sách 37 ID gốc.

8. Mô hình thực thi — Claude sẽ chạy các case này thế nào (giai đoạn sau, sau khi duyệt)

Công cụ sẵn có hiện tại: Browser automation tool (điều khiển được trình duyệt thật, có thể navigate/click/đọc DOM/chụp screenshot — dùng cho hpay-admin, một SPA React chạy trên web); gọi HTTP/curl trực tiếp vào API backend Go (dùng cho mọi endpoint trong openapi.yaml, không cần UI). Không có simulator hay thiết bị thật cho Expo/React Native — hpay-mobile là app di động, Claude không nhìn thấy và không bấm được màn hình của nó qua bất kỳ công cụ hiện có nào.

9. Rollout & risk

Rủi ro thấp ở giai đoạn plan này — chưa tạo file, chưa chạy gì. Rủi ro cần lưu ý cho giai đoạn kế tiếp (tạo file Excel thật): (1) 124 case là ước lượng sàn, số thật có thể lên ~150 khi soạn chi tiết từng dòng, cần thời gian tương ứng; (2) nhóm A-series (admin edge case) chưa có ID chính thức tập trung ở đâu — sheet 05 sẽ là nguồn xác lập ID đó lần đầu, cần đối chiếu kỹ với các đoạn rải rác trong src/admin/docs/plans/*/implementation-plan.html để không đặt trùng/lệch ý nghĩa ID đã dùng; (3) việc Claude tự "Pass" một case PARTIAL mà chưa có người xác nhận phần UI là rủi ro báo cáo sai — quy tắc cứng: PARTIAL không bao giờ tự chuyển Pass, chỉ chuyển Blocked chờ người.

10. Execution checklist (khi được duyệt, cho giai đoạn kế tiếp)

  1. Review 2 tài liệu plan này cùng người dùng — chờ phản hồi rõ ràng trước khi làm bất cứ điều gì tiếp.
  2. Nếu duyệt: tạo D:\hpay\hpay-docs\qa\test-cases\, sinh 5 file .xlsx theo đúng schema mục 4, dữ liệu soạn từ nội dung FEATURES + danh sách 37 edge ID.
  3. Mỗi file có thêm 1 sheet "Read Me" giải thích schema cột + legend Executor, để người dùng khác team cũng đọc hiểu không cần quay lại tài liệu plan này.
  4. Sau khi có file: chạy thử 1 case AUTO-API + 1 case AUTO-WEB làm smoke test cho quy trình thực thi, trước khi chạy hết 124 case.
  5. Không tự ý mở rộng phạm vi (framework tự động, mobile device farm...) — nằm ngoài scope đã thống nhất.
