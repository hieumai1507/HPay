7. Decisions & trade-offs

Quyết địnhPhương án khácVì sao
Đặt bộ Excel + plan trong hpay-docs, không phải 1 trong 3 repo codeĐặt trong hpay-backend (repo "nặng" nhất) theo đúng khuôn docs/plans/<feature>/ đã dùng cho mọi feature khácTest case chạm cả 3 repo trong cùng 1 kịch bản (vd. ký duyệt: mobile UI của checker + API backend); nhét vào 1 repo code sẽ khiến 2 repo còn lại "không biết" bộ test tồn tại. hpay-docs đã đóng vai trò index liên-repo sẵn.
5 file, khớp đúng 4 nhóm vai trò + 1 sheet edge-case riêngGộp hết vào 1 file nhiều sheet, hoặc chia theo repo code (3 file: backend/mobile/admin)Chia theo repo code sẽ làm vỡ tính năng xuyên-repo (1 chức năng thường chạm ≥2 repo) — chia theo vai trò nghiệp vụ (giống functional-overview) giữ đúng góc nhìn người dùng cuối, dễ đối chiếu ngược tài liệu gốc. 5 file riêng thay vì 1 file nhiều sheet để mỗi role-owner (QA mobile, QA admin...) mở đúng 1 file cần, không phải kéo qua nhiều sheet.
Sheet 05 edge-case tách riêng, không chỉ dựa vào cột Related Edge ID ở sheet 01-04Chỉ dùng cột J, không có sheet riêng — tra cứu bằng filterNhiều edge case (race condition, đa-actor, timing) cần mô tả kịch bản dài hơn khuôn 1 dòng "case chức năng" thông thường cho phép, và cần 1 "bảng tổng kiểm" đối chiếu đủ 37/37 ID — filter rải rác qua 4 file dễ sót.
4 nhãn Executor cứng (AUTO-API/AUTO-WEB/PARTIAL/HUMAN) gán sẵn từ lúc thiết kế, không để "tính sau"Không phân loại trước, Claude tự quyết lúc chạy từng caseKhông có simulator mobile là giới hạn cứng đã biết trước — quyết định trước tránh Claude tự nhận "Pass" cho phần UI nó chưa từng thấy; PARTIAL luôn dừng ở Blocked chờ người, không tự suy diễn UI đúng từ response API đúng.
Không thiết kế framework test tự động trong artifact nàyTận dụng luôn cơ hội viết script sinh + chạy test tự động cho các case AUTO-*Ngoài phạm vi được giao — đã có nỗ lực song song khác lo phần tự động hoá (TestEdge_* + gen-api-test); trộn 2 việc sẽ làm plan phình to và khó review trong 1 lượt duyệt.
