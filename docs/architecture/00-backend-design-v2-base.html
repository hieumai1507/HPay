HPay v2 — Thiết kế lại Backend bằng Golang

Phiên bản 2.0 — thay thế bản kế hoạch Node.js. Bổ sung: schema chặt chẽ hơn (double-entry ledger, outbox, idempotency), module Maker-Checker học từ engine DEH, và bộ AI automation (Claude Code skills + AI runtime + CI/CD).

1. Đánh giá engine DEH — lấy gì, bỏ gì

Docs DEH mô tả một Corporate Request-Approval engine (maker-checker authorization matrix). Đánh giá từng concept:

Concept trong DEH Đánh giá Quyết định cho HPay
Maker-Checker theo policy tiers (Policy.tiers, buildApprovalRecord) Đây là nghiệp vụ fintech thật, gần như mọi corporate banking đều có. Điểm sáng nhất của docs. Lấy. Xây module Business Wallet: maker tạo lệnh, checker duyệt theo policy matrix.
TransactionTrail giữ pending state tách khỏi ledger cuối (Transaction) Tách "yêu cầu giao dịch" khỏi "bút toán tài chính" là pattern đúng — ledger chỉ ghi khi đã chốt. Lấy, nhưng gọn hơn: transactions (trạng thái) + ledger_entries (bút toán double-entry, immutable).
TransactionApprove snapshot policy + push checker trong ACID session Snapshot policy tại thời điểm tạo lệnh chống race khi admin sửa policy giữa chừng; push checker trong transaction chống parallel-approve. Lấy nguyên. approval_requests.policy_snapshot (JSONB) + approve trong SELECT ... FOR UPDATE.
Pubsub VERIFY_TRANSACTION bắc cầu async từ approve → core engine Đúng hướng event-driven, khớp luôn với Workflow Engine sẵn có của HPay. Lấy, generalize thành cơ chế resume workflow: approve xong → publish event → engine chạy tiếp các step tài chính.
Auth bypass sau checker approval (engineVerifyTransaction bỏ qua auth đơn lẻ) Hợp lý về nghiệp vụ nhưng cách làm (flag bypass trong core) dễ thành lỗ hổng. Sửa lại: không bypass bằng flag; workflow instance ở trạng thái waiting_approval chỉ resume được bởi event nội bộ từ approval module — quyền nằm ở state machine, không phải if-else.
NeonMessage / fieldBuilder / TransDefinition mapping động Framework mapping field cấu hình được — mạnh nhưng quá phức tạp cho app portfolio, khó giải thích trong phỏng vấn. Bỏ. Dùng struct Go + validator tag là đủ và type-safe hơn.
SOTP / BioAuthMatrix / CustomerStatistic Nhiều hạ tầng, ít giá trị demo. Bỏ, giữ OTP mock (log ra console) + bảng otp_challenges đúng chuẩn (hash, expiry, attempts).

Kết luận: engine này đáng tham khảo. Giá trị lớn nhất là human-in-the-loop approval gate — thứ workflow engine v1 của bạn chưa có (v1 chỉ có auto-steps). HPay v2 sẽ hợp nhất: maker-checker trở thành một step type human_approval trong workflow definition, không phải hệ thống riêng.

Nguyên tắc thiết kế chặt chẽ (khác v1)

  1. Tiền là BIGINT đơn vị nhỏ nhất (VND: đồng). Không bao giờ dùng float. Không có cột balance trong users — số dư chỉ sống ở wallets, và wallets.balance là derived value được kiểm chứng bởi ledger_entries.
  2. Double-entry: mọi giao dịch sinh ≥2 bút toán, tổng debit = tổng credit. Nạp tiền cũng double-entry (đối ứng với ví hệ thống SYSTEM_CASH_IN).
  3. Idempotency: mọi API ghi nhận Idempotency-Key header, unique constraint trong DB — client retry không tạo giao dịch đôi.
  4. Transactional Outbox: event chỉ được publish ra Redis sau khi DB transaction commit (ghi vào bảng outbox cùng transaction, relay đọc và publish). Chống mất event / event ma.
  5. Lock ordering: khi debit+credit 2 ví, luôn SELECT FOR UPDATE theo thứ tự wallet_id tăng dần → không deadlock.
  6. Policy snapshot: approval matrix được chụp vào approval_requests.policy_snapshot lúc tạo lệnh; sửa policy không ảnh hưởng lệnh đang chờ (E09).
  7. State machine có kiểm soát: mọi chuyển trạng thái transaction/workflow qua 1 hàm duy nhất có bảng transition hợp lệ; chuyển sai → error, không âm thầm ghi đè.

3.2. Ví & sổ cái (double-entry)

CREATE TYPE owner_type AS ENUM ('user','organization','system');

CREATE TABLE wallets (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_type      owner_type NOT NULL,
    owner_id        UUID,                          -- NULL cho ví system
    system_code     VARCHAR(40),                   -- 'SYSTEM_CASH_IN', 'SYSTEM_FEE'...
    currency        CHAR(3) NOT NULL DEFAULT 'VND',
    balance         BIGINT NOT NULL DEFAULT 0,
    version         BIGINT NOT NULL DEFAULT 0,     -- optimistic lock cho read-path
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT balance_non_negative CHECK (system_code IS NOT NULL OR balance >= 0),
    CONSTRAINT owner_or_system CHECK (
        (owner_type = 'system' AND system_code IS NOT NULL AND owner_id IS NULL) OR
        (owner_type <> 'system' AND owner_id IS NOT NULL AND system_code IS NULL)
    ),
    UNIQUE (owner_type, owner_id, currency),
    UNIQUE (system_code)
);
-- Ví system được phép âm (ví dụ SYSTEM_CASH_IN âm dần khi user nạp tiền) — đúng bản chất kế toán.

CREATE TYPE txn_type   AS ENUM ('topup','p2p','org_disbursement','fee','reversal');
CREATE TYPE txn_status AS ENUM ('created','pending_approval','processing','completed','failed','reversed');

CREATE TABLE transactions (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ref_code         VARCHAR(24) NOT NULL UNIQUE,        -- mã hiển thị cho user, ví dụ MP26070800001
    idempotency_key  VARCHAR(64) NOT NULL UNIQUE,
    type             txn_type NOT NULL,
    status           txn_status NOT NULL DEFAULT 'created',
    sender_wallet_id   UUID NOT NULL REFERENCES wallets(id),
    receiver_wallet_id UUID NOT NULL REFERENCES wallets(id),
    amount           BIGINT NOT NULL CHECK (amount > 0),
    fee              BIGINT NOT NULL DEFAULT 0 CHECK (fee >= 0),
    currency         CHAR(3) NOT NULL DEFAULT 'VND',
    note             VARCHAR(255),
    initiated_by     UUID NOT NULL REFERENCES users(id), -- maker (với org txn)
    failure_reason   TEXT,
    metadata         JSONB NOT NULL DEFAULT '{}',
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at     TIMESTAMPTZ,
    CONSTRAINT no_self_transfer CHECK (sender_wallet_id <> receiver_wallet_id)
);
CREATE INDEX idx_txn_sender   ON transactions (sender_wallet_id, created_at DESC);
CREATE INDEX idx_txn_receiver ON transactions (receiver_wallet_id, created_at DESC);
CREATE INDEX idx_txn_status   ON transactions (status) WHERE status NOT IN ('completed','failed');

CREATE TYPE entry_direction AS ENUM ('debit','credit');

-- Sổ cái immutable: chỉ INSERT, không UPDATE/DELETE (enforce bằng trigger + quyền DB)
CREATE TABLE ledger_entries (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    transaction_id  UUID NOT NULL REFERENCES transactions(id),
    wallet_id       UUID NOT NULL REFERENCES wallets(id),
    direction       entry_direction NOT NULL,
    amount          BIGINT NOT NULL CHECK (amount > 0),
    balance_after   BIGINT NOT NULL,               -- audit: số dư ví sau bút toán
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_ledger_wallet ON ledger_entries (wallet_id, id);
-- Invariant (kiểm bằng test + recon job): với mỗi transaction_id,

4. Workflow Engine Spec (Go)

4.1. Định nghĩa step — thêm loại human_approval

Khác biệt lớn nhất so với v1: step có type. Step auto chạy qua handler như cũ; step human_approval treo workflow cho tới khi approval module resume — đây chính là chỗ hợp nhất engine DEH vào.

Ràng buộc F6 (implemented): step đầu tiên của mọi definition BẮT BUỘC là type: auto — engine Start() dispatch thẳng step đầu vào handler stream, nên một definition mở đầu bằng human_approval không có nghĩa (chưa có gì để treo). Engine validate điều này ngay lúc parse (ParseSteps).

4.3. Cơ chế chạy (Redis Streams)

  • Engine publish workflow.step.start vào stream wf:steps:{handler} (qua outbox relay).
  • Mỗi handler là một consumer group riêng: XREADGROUP → xử lý → XACK. Message chưa ACK sau timeout_ms được XAUTOCLAIM bởi worker khác → at-least-once; handler phải idempotent (check step_executions attempt hiện tại trước khi làm side-effect).
  • Handler xong → publish workflow.step.completed / workflow.step.failed vào stream wf:events. Engine (consumer group engine) nhận, ghi step_executions, quyết định bước kế: next step, retry (backoff lũy tiến), hoặc chạy on_failure.
  • Compensation (saga): on_failure: compensate → instance chuyển compensating, engine chạy ngược các step đã xong có bút toán (DEBIT đã chạy → post bút toán đảo, không xóa ledger) → compensated, transaction → failed.
  • human_approval: engine gặp step này → set instance waiting_approval, gọi PauseHook — approval module (implement hook) tạo approval_requests (snapshot policy khớp org + amount) và set transaction pending_approval, TẤT CẢ trong cùng DB transaction với việc treo instance, rồi dừng.
  • Resume (F6, implemented): không có event type riêng. Khi request finalize (đủ chữ ký), approval module tự ghi step_executions cho đúng step WAIT_APPROVAL rồi phát outbox workflow.step.result chuẩn (giống hệt kết quả của một auto step) trong cùng transaction quyết định duyệt — engine OnResult nhận, advance tiếp DEBIT → CREDIT → CONFIRM như bình thường. Guard trạng thái được nới để chấp nhận kết quả từ waiting_approval khi step đúng là human_approval, chặt cho auto step. Cách này tái dùng nguyên đường ống F4 (outbox → wf:events → OnResult, đã idempotent theo E06) thay vì thêm consumer/event type mới như bản thiết kế gốc — bản generalize thực tế của pubsub VERIFY_TRANSACTION bên DEH.

4.4. Wallet handler — đoạn ACID quan trọng nhất

// DEBIT + CREDIT trong 1 DB transaction, lock theo thứ tự wallet_id để tránh deadlock
func (h *WalletHandler) transfer(ctx context.Context, tx pgx.Tx, t Txn) error {
    ids := []uuid.UUID{t.SenderWalletID, t.ReceiverWalletID}
    slices.SortFunc(ids, compareUUID)                       // lock ordering
    rows, _ := tx.Query(ctx,
        `SELECT id, balance FROM wallets WHERE id = ANY($1) FOR UPDATE`, ids)
    // ... kiểm số dư, rồi:
    // UPDATE wallets SET balance = balance - $amt, version = version + 1 WHERE id = sender
    // UPDATE wallets SET balance = balance + $amt, version = version + 1 WHERE id = receiver
    // INSERT ledger_entries (debit sender, credit receiver, balance_after)
    // INSERT outbox ('workflow.step.completed')
    return nil // commit tất cả hoặc không gì cả
}

5. Module Maker-Checker (approval/)

5.1. Luồng 3 pha — map từ DEH sang HPay

5.2. evaluateApprovalLogic phiên bản Go

// Tính từ policy_snapshot + approval_actions, thuần túy — dễ unit test
func Evaluate(snapshot PolicySnapshot, actions []Action) Decision {
    for _, a := range actions {
        if a.Action == Reject { return Decision{Status: Rejected} }
    }
    for _, tier := range snapshot.Tiers {                    // level tăng dần
        n := countApprovals(actions, tier.Level)
        if n < tier.RequiredApprovals {
            return Decision{Status: Pending, CurrentLevel: tier.Level}
        }
    }
    return Decision{Status: Approved}                        // isFullyApproved
}

Chống race giống DEH nhưng bằng Postgres: hai checker bấm approve cùng lúc → cả hai cùng FOR UPDATE trên row approval_requests, chạy tuần tự, UNIQUE (request_id, checker_id) trên approval_actions chặn double-act (test TestEdge_E08_CheckerRaceSingleFinalize).

5.3. Điểm sửa so với DEH (nói được trong phỏng vấn)

DEH bypass auth ở core engine sau khi checker duyệt (engineVerifyTransaction bỏ qua processVerifyStepV2 khi serviceType = corporate). HPay không cần flag bypass: bước tài chính chỉ chạy được khi state machine đi qua WAIT_APPROVAL hợp lệ, và event resume chỉ phát sinh từ approval module trong cùng DB transaction với quyết định duyệt. Quyền được mã hóa vào cấu trúc state machine, không phải điều kiện if trong code — an toàn hơn và dễ audit hơn.

KYC scoring — thay hàm random của v1 bằng Claude API thật, có fallback:

Phân loại theo verdict: score ≥ 85 → auto_approved; 50–85 → manual_review (vào queue admin kèm ai_reasons để reviewer đọc); < 50 → rejected. KYC cũng chạy qua workflow engine (definition kyc_verification) → tái sử dụng retry/timeout/log.

Fraud detection hybrid — rule engine trước (rẻ, deterministic, giải thích được): velocity 5 phút, amount gấp N lần trung bình 30 ngày, giờ bất thường, receiver mới. Rule cho score; vùng xám (40–70) mới gọi LLM tổng hợp context giao dịch → trả verdict + giải thích tiếng Việt, lưu vào fraud_flags.reasons cho admin đọc. Điểm phỏng vấn: "LLM không quyết định chặn tiền — chỉ hỗ trợ con người review; quyết định cứng thuộc về rule deterministic."

Recon summary — sau mỗi run đối soát, gọi LLM sinh đoạn tóm tắt nguyên nhân lệch (ví dụ "3 giao dịch missing_external đều trong khung 23:58–00:02, khả năng lệch cutoff ngày") đính vào báo cáo.

10. Điểm "sáng" khi phỏng vấn (cập nhật cho v2)

  1. Học từ production system: "Em tham khảo engine maker-checker của một corporate wallet thật, nhận diện được pattern tốt (policy snapshot, ACID checker push, async bridge) và cả điểm yếu (auth bypass bằng flag) — em thiết kế lại để quyền nằm trong state machine."
  2. Double-entry ledger: "Số dư không phải một con số được cộng trừ — nó là hệ quả của sổ cái immutable. Job đối soát nội bộ verify SUM(ledger) = wallets.balance."
  3. Exactly-once effect trên at-least-once delivery: "Redis Streams đảm bảo at-least-once; em đạt exactly-once effect bằng idempotency key + attempt check trong step handler."
  4. Transactional outbox: "Event không bao giờ phát trước khi DB commit, và không bao giờ mất sau khi commit."
  5. Human-in-the-loop workflow: "Workflow engine của em treo được instance chờ con người duyệt theo authorization matrix nhiều tầng, rồi resume bằng event — cùng một engine chạy cả luồng tự động lẫn luồng cần phê duyệt."
  6. AI đúng chỗ: "AI dùng ở 3 tầng: tự động hóa dev bằng Claude skills, hỗ trợ nghiệp vụ (KYC scoring, fraud explain), và gác cổng CI. Nhưng quyết định tài chính cứng luôn là rule deterministic + con người."
