Solution Architecture — hpay-backend (Golang)

Doc này là kiến trúc giải pháp chính thức cho repo hpay-backend. Phần domain model, schema SQL, workflow engine spec, maker-checker đã định nghĩa đầy đủ tại 00-backend-design-v2-base.md — doc này KHÔNG lặp lại, chỉ tham chiếu và bổ sung các tầng còn thiếu: security, non-functional requirements, ma trận edge case xử lý giao dịch, deployment, observability.

1. Phạm vi & vai trò trong hệ thống

3. Security Architecture

3.1. Authentication

Mục Quyết định Ghi chú
Password argon2id (t=3, m=64MB, p=2) Không bcrypt vì muốn thể hiện hiểu memory-hard
Token JWT access 15 phút + refresh 30 ngày (rotate mỗi lần dùng) Refresh token lưu hash trong bảng refresh_tokens, phát hiện reuse → revoke cả chuỗi (theft detection)
Device binding device_id gửi kèm lúc login, lưu vào claim Giao dịch từ device lạ → fraud rule NEW_DEVICE
OTP Bảng otp_challenges (base doc §3.4): hash, TTL 120s, max 3 attempts, rate-limit tạo 1/30s Dev/demo: code log ra console + trả trong response khi ENV=dev
Admin auth Tách bảng admin_users + JWT audience riêng (aud=admin) Token mobile không bao giờ gọi được API admin dù lộ

3.2. Authorization (3 lớp)

  1. Middleware RBAC: route group gắn role tối thiểu — /v1/admin/* cần admin_users, /v1/org/* cần membership + role đúng (maker/checker/admin trong org_members).
  2. Row-level trong query: mọi query dữ liệu user luôn có điều kiện owner (WHERE w.owner_id = $current_user) — viết sẵn trong sqlc queries, không tin handler.
  3. State machine: hành động nhạy cảm (approve, retry workflow) chỉ hợp lệ khi record đang ở state cho phép — enforce trong DB transaction, không phải chỉ ở API.

3.3. API hardening

  • Rate limit theo (IP, user): login 5/phút, OTP 1/30s, transfer 10/phút — Redis sliding window.
  • Idempotency-Key bắt buộc trên mọi POST tạo giao dịch; key trùng → trả lại response cũ (lưu response snapshot 24h).
  • Input validation 2 tầng: DTO binding (go-playground/validator) + domain invariant (amount > 0, ≤ hạn mức KYC tier).
  • Response không leak: lỗi 4xx/5xx trả mã lỗi chuẩn (ERR_INSUFFICIENT_BALANCE), không trả stack trace/SQL; số dư người khác không bao giờ xuất hiện trong response tra cứu người nhận (chỉ tên đã mask: Nguyễn V** A).
  • Security headers + CORS allowlist đúng origin của admin SPA; mobile không cần CORS.
  • Secrets qua env (12-factor), không có trong repo; .env.example đầy đủ key.
  • Audit log: bảng audit_logs(actor_id, actor_type, action, resource, before, after, ip, created_at) — ghi cho mọi hành động admin và checker.

3.4. Data protection

  • PII (số CMND trích từ KYC) mã hóa cột bằng AES-GCM, key từ env (demo KMS-style envelope: data key mã hóa bằng master key).
  • Ảnh KYC lưu object storage giả lập (thư mục local / MinIO), URL ký thời hạn 5 phút khi admin xem.
  • Log: middleware tự mask các field password, otp, balance — enforce bằng slog ReplaceAttr, được fintech-review skill kiểm.

4. Ma trận Edge Case xử lý giao dịch (bắt buộc có test)

# Tình huống Cơ chế xử lý Kết quả kỳ vọng
E01 Client gửi trùng request transfer (double-tap / retry mạng) Idempotency-Key UNIQUE 1 giao dịch duy nhất, request 2 nhận lại response cũ
E02 2 giao dịch cùng lúc rút từ 1 ví, tổng vượt số dư SELECT FOR UPDATE tuần tự hóa 1 thành công, 1 fail ERR_INSUFFICIENT_BALANCE; balance không âm (CHECK constraint là chốt chặn cuối)
E03 A→B và B→A đồng thời Lock ordering theo wallet_id Không deadlock, cả 2 hoàn tất
E04 Worker chết giữa chừng sau khi DEBIT xong, chưa CREDIT Redis Streams chưa XACK → XAUTOCLAIM giao worker khác; handler idempotent (check step_executions) Step CREDIT chạy tiếp, không debit lần 2
E05 DB commit xong nhưng publish event thất bại Transactional outbox — event nằm trong DB, relay publish lại Không mất event
E06 Event bị publish 2 lần (relay retry) Consumer check step_executions (instance, step, attempt) trước side-effect Xử lý đúng 1 lần
E07 CREDIT fail vĩnh viễn sau khi DEBIT thành công (ví nhận bị khóa giữa chừng) Saga compensation: post bút toán đảo, transaction → failed, user nhận notify hoàn tiền Ledger cân, có vết đầy đủ (không xóa entry nào)
E08 Checker A và B bấm approve cùng lúc ở tier cần 1 approval FOR UPDATE trên transaction_approvals + UNIQUE(approval_id, checker_id) 1 action ghi nhận finalize, action sau nhận ERR_ALREADY_FINALIZED
E09 Admin sửa policy khi lệnh đang chờ duyệt policy_snapshot chụp lúc tạo Lệnh cũ theo policy cũ, lệnh mới theo policy mới
E10 Lệnh org chờ duyệt quá 24h expires_at + cron quét → approval expired, workflow fail sạch Không có lệnh treo vĩnh viễn, maker được notify
E11 OTP sai 3 lần attempts >= max_attempts → challenge vô hiệu, phải xin challenge mới; 5 challenge fail liên tiếp → khóa approve 15 phút Chống brute-force
E12 User bị khóa (fraud) khi giao dịch đang ở giữa workflow Step VALIDATE đã qua nhưng mọi step wallet re-check account_status trong cùng tx Giao dịch fail có kiểm soát, compensation nếu cần
E13 Số tiền 0, âm, hoặc quá hạn mức KYC tier Validator + CHECK constraint Từ chối trước khi tạo workflow
E14 Transfer đến chính mình CHECK no_self_transfer + validate ở API ERR_SELF_TRANSFER
E15 Nạp tiền: bank callback (giả lập) đến 2 lần Idempotent theo ref_code sao kê Cộng tiền đúng 1 lần; lần 2 ghi nhận duplicate cho recon
E16 Clock skew / transaction cắt ngang nửa đêm Recon so khớp theo ref_code chứ không chỉ theo ngày; item lệch cutoff phân loại riêng Không báo lệch giả
E17 Redis down toàn bộ API tạo transaction vẫn ghi DB + outbox; engine dừng tiến độ, instance ở trạng thái đang có Không mất dữ liệu; Redis lên lại → relay + XAUTOCLAIM tự chạy tiếp. Health check báo degraded
E18 Migration mới làm hỏng schema CI job migrate up+down trên DB sạch trước khi merge Không tới được prod

Mỗi dòng E* phải có ít nhất 1 integration test tương ứng (testcontainers), đặt tên TestEdge_E01_... — CI fail nếu thiếu (script đếm coverage theo danh sách).

5. Non-Functional Requirements

Nhóm Yêu cầu Cách đạt
Consistency Ledger luôn cân; balance = derived từ ledger ACID + recon nội bộ hằng ngày (SUM ledger vs wallets.balance)
Latency p95 API đọc < 100ms, transfer end-to-end < 2s (qua 4 step async) Index đúng (base doc §3), consumer prefetch
Throughput mục tiêu demo 100 TPS transfer trên laptop Load test bằng k6, kết quả để trong README
Availability Single-node chấp nhận được (portfolio), nhưng không mất dữ liệu ở mọi failure Outbox + Streams + idempotency (E04–E06)
Observability Trace được 1 giao dịch từ API → từng step request_id + transaction_id propagate qua mọi log/event; endpoint admin xem timeline
Auditability Mọi thay đổi trạng thái có actor + timestamp step_executions, approval_actions, audit_logs

6. Cấu trúc repo hpay-backend

Theo đúng base doc §7 (cmd/, internal/, db/migrations/, .claude/skills/, .github/workflows/). Bổ sung:

src/backend/
├── api/openapi.yaml          # contract-first; FE codegen client từ file này
├── deployments/
│   ├── docker-compose.yml    # postgres, redis, minio, backend
│   └── Dockerfile            # multi-stage → distroless
├── scripts/
│   ├── loadtest/k6-transfer.js
│   └── check-edge-tests.sh   # CI: đối chiếu E01–E18 với test hiện có
└── docs/ → symlink hoặc copy từ ../docs khi cần đóng gói riêng repo

Contract-first: api/openapi.yaml là nguồn chân lý cho cả 3 repo. Backend validate handler khớp spec (oapi-codegen), mobile/admin sinh TypeScript client (openapi-typescript). Đổi API = sửa spec trước → cả 3 repo thấy diff.
