Feature Extensions v2.1 — học từ TMDS Wallet & MoMo, giữ hồn "ví Mỹ"

Nguồn tham khảo: TMDS Wallet Flow Overview (ví retail production tại Thái Lan — engine 3 bước, GL, settlement, 18 nhóm tính năng) và các pattern của MoMo/Venmo/Cash App/Revolut. Nguyên tắc: core logic HPay giữ nguyên (workflow engine event-driven, double-entry ledger, maker-checker human-in-the-loop, outbox, idempotency). Doc này chỉ bổ sung, không thay thế thiết kế ở doc 00/01.

2. Tính năng mới (giữ vibe ví Mỹ)

2.1. Request Money — "Xin tiền / Nhắc nợ" (P1 ⭐ chủ lực)

stateDiagram-v2
  [*] --> pending : requester tạo yêu cầu\n(push + inbox badge, TTL 72h)
  pending --> paid : payer trả qua engine P2P\n(gắn transaction_id)
  pending --> declined : payer từ chối
  pending --> canceled : requester hủy
  pending --> expired : quá 72h (cron quét)
  paid --> [*]
  declined --> [*]
  canceled --> [*]
  expired --> [*]
  note right of paid : Split Bill = N requests\ncùng split_group_id —\ntheo dõi ai đã trả

Venmo Request + MoMo nhắc nợ, chạy trên hạ tầng sẵn có — Stage 1 tạo yêu cầu, Stage 2 người trả thanh toán qua đúng workflow p2p_transfer hiện hữu:

CREATE TYPE money_request_status AS ENUM ('pending','paid','declined','expired','canceled');
CREATE TABLE money_requests (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    requester_id   UUID NOT NULL REFERENCES users(id),
    payer_id       UUID NOT NULL REFERENCES users(id),
    amount         BIGINT NOT NULL CHECK (amount > 0),
    note           VARCHAR(255),
    split_group_id UUID,                              -- NULL nếu không phải chia bill
    status         money_request_status NOT NULL DEFAULT 'pending',
    transaction_id UUID REFERENCES transactions(id),  -- gắn khi paid
    expires_at     TIMESTAMPTZ NOT NULL,              -- mặc định 72h
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT no_self_request CHECK (requester_id <> payer_id)
);

Kèm Split Bill: chọn N người + tổng tiền → chia đều/tùy chỉnh → sinh N money_requests cùng split_group_id, màn theo dõi ai đã trả. UI: inbox badge, swipe để trả nhanh, avatar stack kiểu Venmo.

2.2. Vaults — hũ tiết kiệm (P2, MoMo "Túi Thần Tài" / Revolut Vault)

Schema wallets đã sẵn owner_type+owner_id+currency unique — nới thành nhiều ví/user bằng cột purpose:

ALTER TABLE wallets ADD COLUMN purpose VARCHAR(20) NOT NULL DEFAULT 'main';  -- main | vault
ALTER TABLE wallets ADD COLUMN label   VARCHAR(60);                          -- "Du lịch Đà Lạt 🏔"
-- unique đổi thành (owner_type, owner_id, currency, purpose, label)

Chuyển main↔vault là transaction type vault_move chạy qua engine như thường (2 bút toán, cùng invariants). Stretch: round-up — mỗi giao dịch chi lẻ tự bỏ phần làm tròn vào vault (thêm 1 step ROUND_UP optional trong definition — đúng chỗ khoe engine cấu hình được).

2.3. Approval engine tổng quát hóa (P1 — nâng cấp kiến trúc)

Đổi transaction_approvals → approval_requests với subject_type (org_transaction | admin_reversal | account_lock | policy_change), giữ nguyên policy snapshot + evaluate + OTP. Admin muốn reversal/khóa tài khoản → tạo request → admin khác duyệt (đúng nguyên tắc TMDS: Maker ≠ Checker cả trong nội bộ vận hành). Màn admin "My Tasks" = hàng đợi chờ mình duyệt.

2.4. Fee engine gọn (P1)

CREATE TABLE fee_policies (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    txn_type    txn_type NOT NULL,
    kyc_tier    kyc_status,                 -- NULL = mọi tier
    fixed_fee   BIGINT NOT NULL DEFAULT 0,
    percent_bp  INT NOT NULL DEFAULT 0,     -- basis points (25 = 0,25%)
    min_fee     BIGINT NOT NULL DEFAULT 0,
    max_fee     BIGINT,
    is_active   BOOLEAN NOT NULL DEFAULT true,
    version     INT NOT NULL DEFAULT 1
);

Fee tính ở step VALIDATE, hiển thị preview trước confirm (học UX enquiry-trước của TMDS), ghi bút toán fee về ví SYSTEM_FEE. Đổi fee qua admin → phải qua approval request (§2.3).

2.5. Scheduled & recurring transfer (P2, Cash App style)

Bảng scheduled_transfers(user_id, receiver, amount, cron_expr, next_run_at) + asynq scheduler tạo transaction chạy workflow như thường. Khoe được: cron → engine → idempotency (key = schedule_id + run_date, không bao giờ chạy đôi).

2.6. Trạng thái processing_async + recovery (P1)

Thêm vào enum txn_status giá trị processing_async; job recover_stuck (asynq, 5 phút/lần) quét workflow_instances ở running/compensating quá ngưỡng → replay step hiện tại (handler idempotent sẵn — E04/E06 đã cover). Map với màn Workflow Monitor "kẹt > 5 phút" trong admin.

2.7. Deploy role (P1, chi phí ~0)

HPay serve --role=api|worker|admin|all: api chỉ mount HTTP public, worker chỉ consume streams + asynq, admin mount admin API + cron endpoints, all cho dev. Demo: chạy 1 lệnh ra 3 process phân vai — trả lời được câu phỏng vấn "monolith này scale thế nào".

2.8. QR có số tiền + payment link (P2, MoMo/Venmo)

QR v2: payload ký HMAC gồm user_id + amount + note + exp. Kèm link HPay.app/pay/<token> share qua chat — mở app vào thẳng màn confirm.

3. Không làm (và vì sao)

Tích hợp biller/telco thật, settlement đa tầng biller→aggregator→bank, SFTP đối soát với bank thật, agent DipChip onboarding, lì xì theo mùa vụ, mini-app ecosystem kiểu MoMo — đều cần đối tác thật hoặc lệch khỏi định vị "ví P2P + business wallet sạch kiểu Mỹ". Portfolio ăn điểm ở độ sâu kỹ thuật của core, không phải độ rộng tính năng.

5. Điểm phỏng vấn mới có được từ vòng này
