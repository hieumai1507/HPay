# HPay Knowledge Base

What the system is and how it behaves **today**, verified against the code. Written for people and agents. Everything is English. **Docs first, code second:** change the docs before changing a design; when docs and code disagree, the code is the fact and the doc gets fixed.

Structure follows three well-known ideas: Diataxis (explanation / reference / how-to are kept apart), arc42 (architecture sections), and domain-driven design (business logic is organized by bounded context). Each page has front matter: `type`, `status` (`verified-against-code`, `from-design-doc`, `unverified`), `last_verified`, `code` (paths that implement it).

## Where to look

| I want to know... | Go to |
|---|---|
| What the product does, for whom | `product/` (feature catalog, roles and permissions, KYC tiers and limits) |
| **Business rules, state machines, invariants** of a part of the system | `domain/` (one page per bounded context: ledger, wallet, transfer-and-fees, workflow-engine, outbox-and-events, service-catalog, approval-maker-checker, organization, reversal, money-requests, identity-and-auth, kyc, fraud-and-recon, ai-integration) |
| How it is built (context, building blocks, runtime flows, deployment, cross-cutting concepts, admin and mobile apps) | `architecture/` |
| Exact facts: tables, endpoints, error codes, env vars, terms | `reference/` (data-model, api, error-codes, configuration, glossary) |
| How to operate a secret or a recovery (PIN pepper: generate, rotate, lose, count) | `runbooks/` |
| How to do a task (set up, run tests, add a migration/endpoint/step, debug a stuck transaction) | `guides/` |
| The rules every change must respect | `constitution.md` (C-01..C-15; checked in every plan and review) |
| Why a decision was made | `adr/` (immutable once accepted; `proposed` until the user approves the design; supersede instead of editing) |
| A bug seen before, how it was fixed, how to recognize it | `bugs/` (`INDEX.md` + one `BUG-NNNN` file per bug) |
| Test strategy, edge-case coverage, security model | `quality/` and `qa/` (QA workbooks, generated by skill `hpay-qa-testcases`) |
| Known defects of the current code | `audit/AUDIT-REPORT.md` |
| What is planned or in progress | `specs/` (feature specs and plans), `planning/PLAN.md`, `planning/BACKLOG.md` (agreed, not scheduled), `handoff/` (baseline, per-wave notes) |
| Old designs and per-feature plans | `history/` (**history, not truth**; see `history/README.md`) |
| Templates for new pages | `_templates/` (domain page, architecture page, ADR, bug record) |
| Documents about other systems | `reference/external/` (git-ignored, never a specification source) |

## How the knowledge base is kept alive

- **Feature or change** (`hpay-feature`): stage 2 classifies the architecture impact, stage 3 requires a constitution check and, for architecture changes, a user-approved `proposed` ADR before any code; stage 9 updates `domain/`, `reference/`, `product/`, `architecture/` as needed and writes an ADR for each real decision.
- **Bug fix** (`hpay-bugfix`): stage 0 searches `bugs/` for the same or a related bug before debugging; stage 7 writes the bug record (symptom, root cause, other places with the same flaw, fix, regression test, how to recognize it again) and corrects the domain pages the bug showed to be wrong.
- A domain page's "Known gaps" section lists where the code differs from the intended behavior, with audit IDs. A gap is removed only when the fix is shipped and tested.

## Reading order for a new agent

1. `../CLAUDE.md` and the `CLAUDE.md` of the app you work on.
2. `domain/<context>.md` for every context you will touch, then `architecture/README.md`.
3. `bugs/INDEX.md` and `audit/AUDIT-REPORT.md` entries for the same area.
4. `handoff/baseline.md` for the current test baseline.

## Writing rules

- English Markdown; diagrams are ```` ```mermaid ```` blocks.
- Every rule or claim cites a file:line, constraint or test; unverified statements go under "Open questions", never in the body.
- Describe what exists, not what is planned. Planned work lives in `specs/` and `planning/`.
- Never present another product or company as the HPay specification.
