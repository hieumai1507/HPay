# Implementation Plan — Checker OTP Result & Conflict Screens

**Feature slug:** `approval-result-screens` · Source: [mockup 03-business.html frame 22 & 23](../../../design/mockups/03-business.html). It ships in the same batch as `docs/plans/backend/approval-cancel/` (the "Cancel order" button on the maker screen), but the two parts are independent of each other — the checker result screens need no new backend and merely re-present the existing `DecideResult` / error-code data.

## 1. Current state (surveyed)

| Component | Reality | Conclusion |
|---|---|---|
| `approval-detail.tsx: handleOtpSubmit` | After approve/reject it only shows `Alert.alert` and then `router.back()` — it does not distinguish "you are the final signature" (frame 22) from "only 1 signature recorded so far (more required)" | ❌ replace with a full-screen result state inside the same component |

| `order-status.tsx` "Cancel order" button | Placeholder `Alert` saying "not yet available" | ❌ wire it to `POST /v1/org/approvals/{id}/cancel` (separate backend plan) |

## 2. Scope & Non-goals

### Ships

- `approval-detail.tsx`: after `useDecideApproval` succeeds, replace the screen content (not an Alert) with one of 2 result states: "Approved — the order is being executed" (if `DecideResult.Status==='approved'`, i.e. you are the final signature) or "Signature recorded — N more people still pending" (if still `pending`); on reject → "Order rejected".
- When `useDecideApproval` fails with `ERR_ALREADY_FINALIZED`/`ERR_ALREADY_ACTED`: show the conflict state (frame 23) — "This order was just processed", chip "Processed · being executed" (or whatever matches the real status re-fetched via `refetch`), and a "Back to queue (N orders left)" button using the count from `useApprovalInbox`.
- `order-status.tsx`: the "Cancel order" button calls the real API through `useCancelApproval`, with a confirmation (2-option Alert) before the call because this action cannot be undone.
- Add `'cancelled'` to the `ApprovalDetail.status` type, the `STATUS_LABEL`/`STATUS_CHIP` maps (2 files), and `buildTimeline` (final step "You cancelled the order").

### Non-goals (defer)

- Push/realtime when a new signature arrives while the screen is being viewed — keep following the existing pull model.
- Splitting into a separate route per state (success/conflict) — use local state inside the same screen, to avoid complicating navigation for content that can be expressed with conditional rendering.
