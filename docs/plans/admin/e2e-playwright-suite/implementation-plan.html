2. Scope & Non-goals

Ships (plan này bao phủ, để implement sau khi duyệt)

  • Playwright project (TypeScript) trong src/admin/e2e/, cấu hình playwright.config.ts, chạy Chromium trong CI.
  • Fixture strategy: mở rộng cmd/seed/main.go (hoặc thêm cờ --profile=e2e) để tạo 2 admin_users cố định với plaintext đã biết, phục vụ maker-checker (My Tasks) và test đồng thời (A01/A05).
  • Auth strategy: hỗn hợp — phần lớn test bootstrap session qua API login thật (không qua form) + đúng 1 test đi qua form LoginPage thật (chi tiết mục "Auth strategy").
  • 8 spec file, một cho mỗi tính năng Admin theo functional-overview: dashboard, KYC queue, fraud monitor, workflow monitor, reconciliation, org/policy, My Tasks, audit log.
  • CI job mới (e2e) trong src/admin/.github/workflows/ci.yml, mirror pattern service-container của hpay-backend, checkout hpay-backend làm sibling để build backend thật.
  • Chiến lược flakiness (retry, wait, trace) + quyết định blocking vs non-blocking giai đoạn đầu.

Non-goals (defer)

  • Cross-browser (Firefox/WebKit) trong CI — chỉ Chromium, xem trade-off ở mục 3.
  • ai-settings, services (Service Catalog), offers (Offer Factory) — không nằm trong 8 mục "Đội vận hành" của functional-overview; để plan E2E riêng nếu cần.
  • Visual regression / screenshot diffing — ngoài phạm vi, có thể thêm sau khi suite hành vi đã ổn định.
  • Load/performance testing — Playwright ở đây chỉ kiểm tra hành vi đúng, không đo tải.
  • Publish Docker image backend lên registry (GHCR) cho CI admin pull — đề xuất ở mục "API changes" §Phương án B nhưng không triển khai đợt này; chọn Phương án A (sibling checkout).

4. Test data / fixtures strategy

Xác nhận premise trong đề bài: mỗi lần CI chạy sẽ có postgres container rỗng hoàn toàn (service container mới, không volume) — đây đã là "fresh DB per CI run" miễn phí, không cần cơ chế dọn dẹp thêm. Vấn đề còn lại là: (a) dữ liệu nền tảng dùng chung, và (b) cô lập giữa các test khi chúng ghi/sửa dữ liệu.

4a. Dữ liệu nền (global setup, chạy 1 lần)

  • Sau khi migrate DB rỗng, chạy đúng 1 lần: go run ./cmd/seed (backend, dựng data nghiệp vụ có sẵn: KYC pending, fraud flag, workflow đa dạng, org + policy) + một bước bổ sung nhỏ tạo 2 admin_users cố định với plaintext biết trước — ví dụ e2e-maker@HPay.dev (role ops) và e2e-checker@HPay.dev (role superadmin), password cố định E2ETest@123. Cách làm: thêm cờ --e2e-admins vào cmd/seed/main.go (tách khỏi seed dev mặc định để không lẫn credential test vào demo) — chi tiết implement thuộc phase sau, đây chỉ là quyết định kiến trúc.
  • Không tạo admin fixture qua migration mới — seed script là đúng chỗ (đã có tiền lệ seed admin đơn ở migration 000001, nhưng thêm 2 tài khoản chỉ-để-test vào migration sẽ rò rỉ vào production schema; seed script chạy trong CI/dev không đụng migration).

4b. Cô lập giữa các test (per-spec, không phải per-test)

  • Read-only spec (Dashboard, Workflow Monitor filters, Audit search, Orgs list) dùng thẳng dữ liệu seed — không cần fixture riêng, chạy song song an toàn.
  • Spec có mutation (KYC approve/reject, Fraud resolve, My Tasks approve/reject, Orgs policy save) tự tạo record của riêng mình trong test.beforeEach bằng cách gọi thẳng API backend thật (không qua UI) với token admin đã mint — ví dụ tạo 1 KYC-pending user mới qua endpoint nội bộ/seed helper thay vì dùng chung user 0900000003 mà mọi spec khác cũng đọc. Named theo test.info().testId để không đụng nhau khi chạy song song 2 worker.
  • Không dùng transaction rollback kiểu test DB (pattern phổ biến ở unit test) vì đây là E2E qua HTTP thật, nhiều service (workflow engine async) — rollback giữa các test sẽ phá vỡ side-effect đã trigger. Chấp nhận dữ liệu cộng dồn trong suốt 1 lần chạy CI, dọn sạch bằng việc container postgres bị huỷ cuối job.

5. Auth strategy — khuyến nghị thật, không trung lập

Khuyến nghị: hỗn hợp có thiên hướng — phần lớn test bootstrap session bằng cách gọi thẳng POST /v1/admin/auth/login qua HTTP (không qua form), lấy access_token, rồi page.addInitScript ghi thẳng vào sessionStorage['hpay-admin-session'] đúng format {token, admin} mà useAdminStore đọc — trước khi navigate vào route cần test. Đúng 1 spec (e2e/login.spec.ts) đi qua form thật.

Vì sao không dùng lại "throwaway Go script mint JWT" như lần verify trước

Lần trước dùng Go script gọi thẳng internal/auth.JWTIssuer.Issue() để mint token, bỏ qua hoàn toàn tầng auth service. Cách đó nhanh nhưng có rủi ro thật cho E2E: nếu ai đó phá vỡ logic AdminService.Login (sai mapping role, quên check status=active, đổi field response...), test vẫn xanh vì không bao giờ chạm code đó. E2E của toàn bộ admin console mà auth service không nằm trong đường test nào là một lỗ hổng coverage đáng kể — auth là thứ đầu tiên mọi phiên phải đi qua.

Vì sao không bắt mọi test đi qua form UI

Form UI (click, type, submit, chờ redirect, chờ toast lỗi nếu có) tốn ~1–2s + round-trip DOM mỗi lần, nhân với hàng chục spec sẽ cộng dồn thành phút chờ vô nghĩa — phần UI login đã được phủ đầy đủ bởi chính login.spec.ts, lặp lại nó ở mọi spec khác không tăng coverage, chỉ tăng thời gian CI và bề mặt flake (network, animation, redirect timing).

7. CI job design (thay cho "API changes" — không có API mới)

Không có schema/API mới ở phía backend hay admin (test suite thuần tiêu thụ API đã có). Phần thiết kế thật nằm ở CI job — sketch bên dưới, chỉ là tài liệu đề xuất, không phải file YAML thật được commit trong đợt plan này.

Quyết định: checkout hpay-backend làm sibling repo trong CI job

Phương án A (khuyến nghị, sketch dưới đây dùng phương án này): job E2E của hpay-admin checkout thêm hieumai1507/hpay-backend vào thư mục con, build binary Go ngay trong job, migrate DB, start server, rồi chạy Playwright nhắm vào server đó. Phương án B (không chọn đợt này): hpay-backend CI tự build & publish Docker image lên registry (GHCR) mỗi lần merge main; hpay-admin CI chỉ docker pull image đã build sẵn — nhanh hơn, tách toolchain, nhưng đòi hỏi việc mới ở hpay-backend (thêm job publish image) chưa tồn tại và không thuộc phạm vi sửa của plan này. Chọn A vì triển khai được ngay trong repo hpay-admin, không cần thay đổi hpay-backend; B ghi lại như cải tiến tương lai (xem Non-goals).

# src/admin/.github/workflows/ci.yml — job mới "e2e" (SKETCH — không phải file commit thật)
e2e:
  runs-on: ubuntu-latest
  services:
    postgres:
      image: postgres:16-alpine
      env: { POSTGRES_USER: HPay, POSTGRES_PASSWORD: HPay, POSTGRES_DB: HPay }
      ports: ["5432:5432"]
      options: >-
        --health-cmd "pg_isready -U HPay" --health-interval 3s --health-retries 10
    redis:
      image: redis:7-alpine
      ports: ["6379:6379"]
      options: >-
        --health-cmd "redis-cli ping" --health-interval 3s --health-retries 10
  env:
    DB_URL: postgres://HPay:HPay@localhost:5432/HPay?sslmode=disable
    REDIS_ADDR: localhost:6379
    E2E_BASE_URL: http://localhost:4173
  steps:
    - uses: actions/checkout@v4
      with: { path: hpay-admin }

    - uses: actions/checkout@v4          # Phương án A: sibling checkout
      with:
        repository: hieumai1507/hpay-backend
        ref: main                        # pin tới tag/SHA đã test nếu muốn giảm rủi ro drift
        path: hpay-backend

    - uses: actions/setup-go@v5
      with: { go-version-file: src/backend/go.mod }
    - uses: sqlc-dev/setup-sqlc@v4
      with: { sqlc-version: "1.27.0" }

    - name: build + migrate + seed backend
      working-directory: hpay-backend
      run: |
        sqlc generate --no-remote
        curl -fsSL https://github.com/golang-migrate/migrate/releases/download/v4.17.1/migrate.linux-amd64.tar.gz | tar xz
        sudo mv migrate /usr/local/bin/
        migrate -path db/migrations -database "$DB_URL" up
        go build -o /tmp/hpay-server ./cmd/server
        DATABASE_URL="$DB_URL" go run ./cmd/seed --e2e-admins   # T4a: data nền + 2 admin fixture

    - name: start backend
      working-directory: hpay-backend
      run: |
        DATABASE_URL="$DB_URL" REDIS_ADDR="$REDIS_ADDR" /tmp/hpay-server &
        npx wait-on http://localhost:8080/healthz -t 30000   # healthcheck trước khi FE build/test chạy

    - uses: actions/setup-node@v4
      with: { node-version: 20, cache: 'npm', cache-dependency-path: src/admin/package-lock.json }
    - name: install + build admin
      working-directory: hpay-admin
      run: |
        npm ci
        npm run build
        npx playwright install --with-deps chromium
    - name: serve admin (preview build)
      working-directory: hpay-admin
      run: npx vite preview --port 4173 &
        npx wait-on http://localhost:4173 -t 15000

    - name: run Playwright
      working-directory: hpay-admin
      run: npx playwright test --project=chromium
      env:
        CI: true

    - uses: actions/upload-artifact@v4     # trace/report khi fail, để debug flake
      if: failure()
      with: { name: playwright-report, path: src/admin/playwright-report/, retention-days: 7 }

Chặn merge: job e2e thêm vào needs của bất kỳ job "gate" tổng hợp nào (hoặc tự nó là 1 required status check trong branch protection của hpay-admin) — giống cách build của hpay-backend khai needs: [lint, test]. Chi tiết bật/tắt "required" ngay từ đầu hay sau, xem mục Rollout.

Blocking hay non-blocking ngay từ đầu — khuyến nghị

Khuyến nghị: non-blocking (không phải required check) trong 1–2 tuần đầu, dùng continue-on-error: true cho job e2e hoặc không thêm vào danh sách required status check của branch protection, kèm thông báo rõ trong PR (comment/summary) khi fail. Sau giai đoạn trial — khi suite chạy ổn định qua nhiều PR liên tiếp không có false-positive do flake — chuyển sang required/blocking. Lý do: đây là suite hoàn toàn mới, full-stack, nhiều thành phần lần đầu phối hợp trong CI (sibling checkout, healthcheck backend thật, seed E2E-only) — nếu bắt buộc pass ngay từ ngày 1, một lỗi hạ tầng CI (không phải lỗi sản phẩm) có thể chặn mọi PR không liên quan, gây mất niềm tin vào gate và áp lực bypass/skip test — rủi ro lớn hơn lợi ích của việc "chặn ngay từ đầu".

Không có migration/schema nào trong plan này → không có rollback DB. Rollback nếu cần: revert PR thêm job CI, không ảnh hưởng code sản phẩm.
