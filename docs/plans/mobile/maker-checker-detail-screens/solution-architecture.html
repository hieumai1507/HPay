Solution Architecture — Maker Status & Checker Signatures

Song hành với implementation-plan.html. Cả 2 màn đọc chung 1 nguồn dữ liệu — GET /v1/org/approvals/{id} — chỉ khác cách trình bày (timeline cho maker, list chữ ký cho checker).

1. Context

flowchart LR
  D["disburse.tsx\n(maker tạo lệnh)"] -->|"push order-status?id="| M["order-status.tsx\n(mới — timeline)"]
  L["approvals.tsx\n(checker inbox)"] -->|"push approval-detail?id="| C["approval-detail.tsx\n(bổ sung khối CHỮ KÝ)"]
  M --> H["useApprovalDetail(id)"]
  C --> H
  H -->|"GET /v1/org/approvals/:id"| API["hpay-backend\nApprovalHandler.Detail"]

2. Main flow

sequenceDiagram
  participant Maker as Maker (order-status.tsx)
  participant Checker as Checker (approval-detail.tsx)
  participant Hook as useApprovalDetail(id)
  participant API as GET /v1/org/approvals/{id}

  Maker->>Hook: mount với id vừa tạo
  Checker->>Hook: mount với id từ inbox
  Hook->>API: fetch
  API-->>Hook: {status, current_level, signatures[], signatures_required, ...}
  Hook-->>Maker: render timeline theo current_level + signatures
  Hook-->>Checker: render khối CHỮ KÝ theo signatures[]

3. State — timeline suy ra từ status + current_level, không lưu state riêng

stateDiagram-v2
  [*] --> StepDone: signature.level < current_level
  [*] --> StepActive: signature.level == current_level AND status = pending
  [*] --> StepWaiting: signature.level > current_level
  StepDone --> [*]
  StepActive --> [*]: chip "Chờ duyệt · x/y chữ ký"
  StepWaiting --> [*]: mờ, chưa tới lượt
  [*] --> Approved: status = approved
  [*] --> Rejected: status = rejected
  [*] --> Expired: status = expired

4. Data model delta

Không có — dùng nguyên response của GET /v1/org/approvals/{id} (xem solution-architecture backend §4).

5. Decisions & trade-offs

6. Invariants touched

Không invariant tài chính nào ở tầng mobile — chỉ hiển thị dữ liệu đọc; luồng duyệt/từ chối (OTP + useDecideApproval) giữ nguyên không đổi.
