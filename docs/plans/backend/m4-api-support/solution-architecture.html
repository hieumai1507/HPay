2. Main flow — QR mint → resolve → transfer

sequenceDiagram
  participant B as Máy B (người nhận)
  participant A as Máy A (người quét)
  participant API as Backend
  B->>API: GET /v1/users/me/qr (JWT B)
  API-->>B: {payload: b64({user_id,name_masked,phone_masked,exp}), signature, expires_at(15')}
  B->>A: chìa QR (offline — nội dung là payload+signature)
  A->>API: POST /v1/qr/resolve {payload, signature} (JWT A, rate-limit 30/min)
  alt signature sai (QR giả / sửa payload)
    API-->>A: 400 ERR_QR_INVALID (check sig TRƯỚC exp — không leak gì)
  else quá TTL
    API-->>A: 410 ERR_QR_EXPIRED
  else hợp lệ
    API-->>A: {name_masked, phone_masked, receiver_token(10'), expires_at}
  end
  A->>API: POST /v1/transactions/transfer {receiver_token, amount, note} + Idempotency-Key
  API->>API: VerifyReceiverToken → user_id B (server-side, client không bao giờ thấy phone thật)
  API->>API: transfer.TransferToUser(...) — luồng F5 nguyên vẹn (validate→fraud→move→confirm)
  API-->>A: 202 {ref_code, ...} → poll như M3

3. Main flow — remind + guard 24h

sequenceDiagram
  participant R as Requester
  participant API as Backend
  participant DB as postgres
  R->>API: POST /v1/money-requests/{id}/remind (JWT)
  API->>DB: UPDATE money_requests SET last_reminded_at=now()
WHERE id AND requester_id=me AND status='pending'
AND (last_reminded_at IS NULL OR < now()-24h) RETURNING id
  alt 1 row
    API-->>R: 200 {last_reminded_at} — payer thấy khi mở inbox (polling)
  else 0 rows
    API->>DB: SELECT để phân loại lỗi
    API-->>R: 404 not-found / 403 not-requester / 409 not-pending / 429 ERR_REMIND_TOO_SOON
  end
  Note over DB: Guard nằm TRONG câu UPDATE — 2 remind đồng thời chỉ 1 thắng,
không cần lock riêng (cùng pattern guard WHERE status của dự án)

Không có state machine mới (money_request_status không đổi; last_reminded_at là metadata, không phải trạng thái).

5. Decisions & trade-offs

Quyết địnhLựa chọn khácVì sao
QR + receiver_token stateless bằng HMAC (tái dùng storage.Signer, thêm hàm generic Sign/VerifyMsg)Bảng qr_tokens trong DB; hoặc JWTSigner đã có, đã test, verify-sig-trước-exp đúng chuẩn; stateless = không dọn rác, không thêm bảng; JWT nặng và lẫn với auth token
Transfer nhận receiver_token oneOf receiver_phone, refactor TransferToUser(receiverID)Endpoint transfer riêng cho QR1 endpoint 1 luồng tiền — idempotency, fee, workflow y hệt; client cũ không vỡ; token purpose sau này tái dùng cho pay-by-counterparty (backlog M3)
Payload QR chứa user_id + masked, KHÔNG chứa phone thậtChỉ chứa token opaqueDoc 02 §5 yêu cầu payload có user_id + phone masked để màn confirm hiển thị không cần round-trip; tiền vẫn chỉ đi được qua token ký
Remind = cột last_reminded_at + guarded UPDATE, không notifications infraBảng notifications + pushDoc 02 §6: polling là đủ cho v1; payer thấy nhắc qua inbox có sẵn; notifications infra là backlog riêng, làm vội sẽ nửa vời
Resolve yêu cầu JWT + RateLimitUser 30/minPublic không authChặn dò/brute-force payload; người quét chắc chắn là user đã đăng nhập (muốn chuyển tiền mà)
