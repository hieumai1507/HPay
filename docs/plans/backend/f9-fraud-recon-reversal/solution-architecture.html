2. Main flow — reversal end-to-end (mảng có tiền, vẽ kỹ nhất)

sequenceDiagram
  autonumber
  actor A as Admin A (maker)
  actor B as Admin B (checker)
  participant API as /v1/admin
  participant APR as approval (F6 core)
  participant LED as ledger.Post
  participant DB as PostgreSQL
  A->>API: POST /reversals {ref_code, reason}
  API->>DB: guard: txn completed? chưa reversed?\nchưa có request? (UNIQUE subject_type+subject_id)
  API->>DB: INSERT approval_requests\n(subject=reversal, org NULL, policy NULL,\nsnapshot {L1×1}, created_by=A, 24h)
  B->>API: GET /admin/approvals (My Tasks)
  B->>API: POST /admin/approvals/{id}/decide {approve}
  API->>APR: AdminDecide: guard B là admin, B ≠ created_by (ERR_SELF_APPROVAL)
  APR->>DB: FOR UPDATE request → insert action\n(UNIQUE chặn double-act) → Evaluate = approved
  APR->>APR: finalize → executor reversal (CÙNG TX)
  APR->>DB: INSERT transactions(type=reversal,\nreversal_of=gốc, status→completed)\n(one_reversal_per_txn chặn lần 2)
  APR->>LED: Post mirror legs từ txn row:\nsender +amount+fee · receiver −amount · SYSTEM_FEE −fee\n(đúng công thức compensate F5 — đã test E07)
  APR->>DB: gốc: completed→reversed (guarded) + audit\n— COMMIT tất cả hoặc không gì
  Note over B,DB: reject → request rejected, txn gốc GIỮ NGUYÊN completed

5. Decisions & trade-offs

Quyết địnhPhương án khácVì sao
Advisory LLM fire-and-forget (goroutine + context riêng, update flag reasons sau)Gọi sync trong handlerFRAUD_CHECK timeout_ms=3000 trong definition đang chạy — LLM 5–15s sẽ nổ timeout và retry vô ích; quyết định chặn/flag đã xong TRƯỚC KHI gọi LLM nên async không đổi semantics (LLM không quyết gì — đúng nguyên tắc §9)
Chặn ở >70 bằng rule thuần, terminal error qua on_failure sẵn cóThêm on_failure=flag_review mới vào engineDocs vùng xám là 40–70 → trên 70 là vùng rule tự tin; on_failure=fail của definition hiện hành cho đúng hành vi (txn fail, compensation không cần vì tiền chưa đi — FRAUD_CHECK đứng trước MOVE_FUNDS); không đổi engine
Recon match ref_code toàn cục, không lọc ngày; lệch ngày ghi detail cutoff_shiftMatch trong ngày + nới cửa sổ ±15'Chính là chữ E16 trong docs 01 ("so khớp theo ref_code chứ không chỉ theo ngày"); cửa sổ giờ nào cũng là heuristic sai được — còn ref_code là định danh tuyệt đối
Reversal không qua workflow engine, executor trong finalize txDefinition reversal_flow 2 stepDoc 04 §1 chốt nguyên văn "bút toán đảo passive, không đi qua engine"; toàn bộ effect (txn mới + ledger + gốc reversed + audit) là MỘT giao dịch ACID — engine không thêm được gì ngoài độ trễ
Mirror legs từ txn row (amount, fee)Đọc ledger_entries gốc rồi đảo từng dòngCùng nguồn chân lý mà Wallet.legs(compensate) F5 dùng — đã chứng minh cân bằng qua E07; txn row bất biến sau completed nên an toàn
approval_requests.created_by / actions.checker_id bỏ FK, giữ NOT NULL2 cột riêng user_id/admin_id + CHECKÍt xâm lấn nhất với code F6 đang chạy (org path giữ nguyên hoàn toàn); integrity theo subject_type enforce ở service (org path check org_members, admin path check admin_users) — đúng chỗ logic đó vốn đã sống
Score/points fraud là int, evidence là text có số liệufloat confidenceGiữ kỷ luật no-float toàn repo; rule threshold là hằng số nguyên đọc được trong 1 dòng code

6. Invariants touched (index.html §8)

Bất biếnF9 giữ bằng cách
Ledger chỉ INSERT; hoàn tiền = giao dịch đảo mới có reversal_ofReversal = txn mới + entries mới qua ledger.Post; không UPDATE/DELETE entry nào; one_reversal_per_txn + guard completed→reversed chặn đảo đôi
Sau completed trạng thái không sửa tại chỗcompleted→reversed là transition DUY NHẤT được phép từ completed (state diagram index §7), guarded WHERE status='completed'
LLM không bao giờ tự quyết chặn tiềnChặn = rule int threshold; LLM chỉ ghi text vào reasons, chạy sau quyết định, lỗi LLM nuốt im
wallets.balance = SUM(ledger)Recon nội bộ mỗi run kiểm đúng đẳng thức này trên mọi ví, lệch → item + ai_summary nêu tên
Maker ≠ Checker cả trong nội bộ vận hành (doc 04 §2.3)AdminDecide chặn created_by == decider (ERR_SELF_APPROVAL) + UNIQUE(request_id, checker_id)
State transition guard WHERE statusResolveFraudFlagGuarded WHERE 'open'; MarkTransactionReversed WHERE 'completed'; run_date UNIQUE làm recon idempotent
Điểm phỏng vấn của phase này: đường nóng và đường nguội tách bạch — fraud rule chạy trong 3ms budget của step, LLM đắt tiền bị đẩy ra ngoài band; recon chứng minh đẳng thức kế toán mỗi đêm thay vì tin vào code; và reversal cho thấy approval framework F6 đúng là hạ tầng dùng chung: thêm một subject mới = 1 executor + 0 dòng sửa core.
