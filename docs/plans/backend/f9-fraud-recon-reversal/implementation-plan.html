F9 Fraud + Recon + Reversal — Implementation Plan

1. Scope & non-goals

3 mảng độc lập, 1 nguyên tắc chung (index.html §9): quyết định cứng về tiền luôn là rule deterministic + con người — LLM chỉ advisory (giải thích fraud, tóm tắt recon), mock fallback khi thiếu key. Reversal theo TMDS (doc 04 §1): bút toán đảo passive, KHÔNG đi qua workflow engine, bắt buộc maker-checker giữa 2 admin — executor đăng ký vào approval framework F6 qua đúng cái RegisterExecutor đã chừa sẵn.

6. Rollout & risk

2 deviation cần anh gật đầu khi duyệt plan: (1) Admin decide không OTP — doc 00 §5 mô tả OTP cho checker, nhưng otp_challenges FK→users; admin đã xác thực aud=admin + password argon2id, và Maker≠Checker vẫn enforce. Nếu muốn OTP admin thật thì cần migration nới FK — đề xuất để A-phases quyết khi làm UI. (2) Rule NEW_DEVICE → NEW_RECEIVER — transactions không lưu device_id; NEW_RECEIVER nằm cùng danh sách docs §8.2 nên vẫn đúng thiết kế, chỉ là chọn 4/5 rule có data.
  • Fraud chặn (>70) dùng đường on_failure=fail CÓ SẴN của definition p2p/org — không sửa definition, không migration engine.
  • LLM advisory sync trong handler nhưng timeout 15s < step timeout 3s? — KHÔNG: FRAUD_CHECK timeout_ms=3000 trong definition! Advisory phải chạy SAU quyết định, fire-and-forget goroutine với context riêng (không giữ step), flag update reasons async. Ghi rõ trong solution-architecture.
  • Excelize là dep mới (~vài MB) — chỉ import trong internal/recon, không ảnh hưởng binary path nóng.
  • Route /v1/files đổi shape — chỉ admin SPA dùng (chưa build), an toàn đổi; openapi cập nhật cùng commit.
  • Reversal executor chạy trong finalize tx của decide — giữ nguyên bất biến "resume/effect commit cùng quyết định" của F6; ledger.Post lock ordering tự lo deadlock.
