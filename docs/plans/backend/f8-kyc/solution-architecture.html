2. Main flow — submit → score → classify → (review)

sequenceDiagram
  autonumber
  actor U as User
  participant API as API /v1/kyc
  participant ST as storage (local)
  participant ENG as Engine
  participant SC as kyc_scorer
  participant CL as kyc_classifier
  actor AD as Admin
  U->>API: POST /kyc/submit (id_card + selfie)
  API->>API: guard: đang pending/manual? đã verified? → 4xx
  API->>ST: ghi 2 ảnh ({request_id}/id_card.jpg, selfie.jpg)
  API->>ENG: tx: INSERT kyc_requests(pending)\n+ users.kyc_status none|rejected→pending (guarded)\n+ engine.Start("kyc_verification", txn=NULL, ctx={kyc_request_id})
  API-->>U: 202 {request_id} — poll GET /kyc/status
  ENG->>SC: SCORE (retry 2, timeout 30s)
  SC->>ST: load 2 ảnh
  SC->>SC: Scorer.Score() → claude hoặc mock\nlỗi mạng/5xx → RetryableError (engine retry+backoff)
  SC->>ENG: output {score, reasons} + SetKYCScore
  ENG->>CL: CLASSIFY
  alt score ≥ 85
    CL->>CL: kyc_requests→auto_approved + users→auto_approved
  else 50 ≤ score < 85
    CL->>CL: kyc_requests→manual_review + users→manual_review\n(vào queue admin kèm ai_reasons)
    AD->>API: GET /admin/kyc?tab=manual (ảnh = signed URL 5')
    AD->>API: POST /admin/kyc/:id/review {approve|reject, reason}
    API->>API: tx: WHERE status='manual_review' (0 rows → 409)\n+ users→verified|rejected + audit_logs
  else score < 50
    CL->>CL: kyc_requests→rejected + users→rejected\n(user được submit lại)
  end

3. State — users.kyc_status (enum có sẵn từ F1, giờ mới chạy đủ vòng)

stateDiagram-v2
  [*] --> none : đăng ký (F2)
  none --> pending : submit KYC
  rejected --> pending : re-submit (re-KYC)
  pending --> auto_approved : CLASSIFY score ≥ 85\n(limit giao dịch lên 100tr — wallet.TxnLimit F3)
  pending --> manual_review : 50 ≤ score < 85
  pending --> rejected : score < 50
  manual_review --> verified : admin approve\n(guarded + audit)
  manual_review --> rejected : admin reject
  auto_approved --> [*]
  verified --> [*]
  note right of manual_review : 2 reviewer đua nhau →\nUPDATE WHERE status='manual_review'\nngười sau 0 rows → 409 (nền cho A01)

5. Decisions & trade-offs

Quyết địnhPhương án khácVì sao
2 step SCORE → CLASSIFY thay vì 1 step làm cả hai1 step gọi LLM rồi phân loại luônTách phần không tất định + chậm + retryable (LLM call) khỏi phần tất định (thresholds): SCORE retry được mà không chạy lại classification; CLASSIFY idempotent thuần nhờ guarded UPDATE; timeline admin (A3) nhìn thấy rõ kẹt ở đâu
Liên kết instance ↔ kyc_request qua workflow context ({kyc_request_id}), không thêm cộtThêm cột kyc_requests.instance_id hoặc workflow_instances.subject_idContext JSONB sinh ra đúng cho việc này (docs 00 §3.3 "dữ liệu truyền giữa các step"); thêm cột generic subject vào workflow_instances là thay đổi schema lớn chưa cần — nếu F9+ cần truy ngược thường xuyên thì đề xuất sửa docs trước
Scorer chọn theo presence của ANTHROPIC_API_KEY, mock deterministic theo hash ảnhCờ cấu hình riêng KYC_SCORER=claude|mockĐúng thiết kế docs 00 §8.2 ("mock fallback khi thiếu key"); hash-based mock cho demo lặp lại được (cùng ảnh → cùng verdict) thay vì random thuần
Score là int 0–100 xuyên suốt Go, ghi vào NUMERIC(5,2)float64 khớp NUMERICKhông có lý do cần thập phân; giữ codebase 100% không-float làm câu chuyện review/phỏng vấn sạch tuyệt đối
Signed URL HMAC (key+exp, secret=JWT_SECRET) cho ảnh, route riêng không cần JWTAdmin endpoint stream ảnh sau RequireAdminSPA render <img src> không gắn được Authorization header — signed URL là auth tự thân, đúng mô tả doc 01 §3.4 "URL ký thời hạn 5 phút"; TTL ngắn giới hạn rò rỉ
Admin auth tối thiểu trong F8 (login + middleware, access-only)Đợi phase admin riêngMaster plan F8 ghi rõ "admin review API" — không có đường login thì API đó không dùng được; JWT issuer F2 đã hỗ trợ audience nên chi phí gần bằng 0; refresh/RBAC chi tiết đến khi A-phases cần
Admin review dùng guarded UPDATE (0 rows → 409), không FOR UPDATESELECT FOR UPDATE như approval F6Review là single-statement transition, không có multi-step evaluation như approval — guard WHERE đủ atomic, ít lock hơn; trả đúng semantics 409 mà A01 (admin repo) cần

Điểm phỏng vấn của phase này: cùng một workflow engine giờ chạy 3 loại luồng — tự động (P2P), human-gate giữa chừng (org approval), và không-transaction (KYC) — chứng minh "transaction_id nullable" của F4 là thiết kế có chủ đích chứ không phải nợ kỹ thuật. Và AI được đặt đúng chỗ: LLM cho điểm, threshold tất định + con người quyết định.
