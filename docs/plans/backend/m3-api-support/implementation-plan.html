📋 Implementation Plan — M3 API Support backend

Phase nhỏ phía backend phục vụ mobile M3 (Core Screens). Nguồn: rà soát plan src/mobile/docs/plans/m3-core-screens phát hiện 4 chỗ client phải "dùng tạm"/hardcode vì thiếu contract — vi phạm luật contract-first 2 chiều. Phase này bổ sung đủ 4 API để mobile không có workaround nào.

1. Scope & non-goals

Ships — 4 thay đổi API (chi tiết §3):

  • A1 — Receiver lookup: GET /v1/users/lookup?phone= trả tên masked để màn Transfer xác nhận người nhận trước khi chuyển.
  • A2 — Counterparty trong history/detail: thêm direction + counterparty_name (masked) + counterparty_phone (masked) vào GET /v1/transactions và GET /v1/transactions/{refCode} — TxnListItem cần "tên đối tác", danh bạ gần đây cần SĐT.
  • A3 — Expose KYC limit: GET /v1/users/me trả {user, txn_limit} — client bỏ hardcode map limit (map trong plan mobile hiện tại đã lệch so với wallet.TxnLimit()).
  • A4 — Failure code trên timeline: GET /v1/transactions/{refCode}/timeline thêm failure_code (ERR_* đã sanitize) khi instance failed/compensated — client map ra message tiếng Việt (M03).

Non-goals: không đổi schema DB (mọi dữ liệu đã có, chỉ join/expose); không thêm search full-text danh bạ; không đổi engine/workflow.

6. Rollout & risk

  • Toàn bộ là additive (field mới + endpoint mới) — không breaking với client hiện có; mobile regenerate schema.d.ts qua npm run gen:api.
  • Risk chính: phone enumeration qua lookup → rate-limit per-user + response không phân biệt lý do 404. Ghi audit_log mỗi lookup.
  • failure_code chỉ map từ allowlist sentinel — không bao giờ trả raw error nội bộ (không leak stack/SQL).
  • Rollback = revert commit (không migration).
