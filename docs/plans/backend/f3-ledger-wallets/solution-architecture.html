F3 Ledger & Wallets — Solution Architecture

1. Context

flowchart LR
  cl["📱 Client (JWT)"] --> mw["RequireAuth\n+ RequireIdempotencyKey (POST tiền)"]
  mw --> wh["wallet handlers\n/v1/wallets · /v1/transactions"]
  wh --> ws["wallet.Service\nEnsureMainWallet · Topup · History"]
  ws --> lg["ledger.Post(tx, txnID, legs)\n⭐ điểm duy nhất được chạm số dư"]

Nguyên tắc trung tâm: ledger.Post là cánh cửa DUY NHẤT làm thay đổi số dư — mọi module (topup hôm nay, engine F5, reversal F9, vault move P2) đều đi qua nó. Không có UPDATE wallets ở bất kỳ đâu khác.

2. Main flow — Topup (sync) & Post

sequenceDiagram
  autonumber
  actor C as Client
  participant H as POST /v1/wallets/topup
  participant W as wallet.Service
  participant L as ledger.Post
  participant DB as PostgreSQL
  C->>H: {amount} + Idempotency-Key + JWT
  H->>W: Topup(userID, amount, key)
  W->>W: validate amount > 0, ≤ hạn mức KYC tier (E13)
  W->>DB: BEGIN
  W->>DB: INSERT transactions (status=processing, key UNIQUE)
  alt key đã tồn tại (23505 — E01)
    W->>DB: ROLLBACK + SELECT txn cũ theo key
    W-->>C: 200 giao dịch cũ (không cộng tiền lần 2)
  else
    W->>L: Post(tx, txnID, [Dr SYSTEM_CASH_IN, Cr ví user])
    L->>DB: SELECT ... FOR UPDATE (sort id — E03)
    L->>L: check âm ví non-system (E02) · sum Dr = sum Cr
    L->>DB: UPDATE balance + INSERT ledger_entries (balance_after dồn)
    W->>DB: UPDATE txn status=completed, completed_at
    W->>DB: COMMIT — tất cả hoặc không gì
    W-->>C: 201 {refCode, status: completed, balance mới}
  end

5. Decisions & trade-offs

Quyết địnhPhương án khácVì sao
Topup sync 1 DB tx, không qua engineCho topup qua workflow như P2PBank mock trả lời tức thì — thêm 4 hop async chỉ để giống nhau là over-engineering; engine dành cho luồng có bước rủi ro (fraud check, approval). Trade-off: 2 code path — chấp nhận, cả 2 đều hội tụ ở ledger.Post
Idempotency bằng UNIQUE constraint + trả txn cũ khi conflictBảng cache response đầy đủĐơn giản, atomic, đủ đúng: client nhận lại giao dịch (thực thể) thay vì response byte-by-byte; response cache thêm khi có nhu cầu thật
balance_after ghi dồn theo thứ tự legs trong 1 lần PostChỉ ghi balance cuốiAudit đọc được từng bước; recon nội bộ so khớp được từng dòng
Hạn mức per-txn const trong codeBảng limit policyF5 sẽ có fee_policies — gộp limit vào đó một thể, tránh làm 2 lần
