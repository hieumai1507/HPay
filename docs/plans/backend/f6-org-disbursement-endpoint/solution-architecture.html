Solution Architecture — Org Disbursement HTTP Endpoint

Pure wiring change: expose the already-implemented org.Service.CreateDisbursement over HTTP. No new domain logic, no schema change. Diagrams below show only the request path this feature adds.

3. State

No new lifecycle. This endpoint only creates the transaction; the existing status machine (already documented in docs/planning/master-plan.html §7) applies unchanged: created → pending_approval → processing → completed | failed, driven entirely inside CreateDisbursement + the workflow engine's WAIT_APPROVAL pause hook. The HTTP layer only ever observes the synchronous return value (status is whatever InsertTransaction set at the moment of response — typically pending_approval once the pause hook has run inline, or created if the caller races ahead of it).

5. Decisions & trade-offs

DecisionAlternatives consideredWhy
Route path POST /v1/org/{id}/transactionsRoute the mobile client's existing target vs. changing mobile to hit the unified /v1/me/transactions/request engine endpoint with a service_codeMobile already calls this exact path and shape; the org group already scopes by {id} the same way members/policies do. Changing mobile would touch a second repo for zero benefit — the service method is org-specific (maker-role check, org wallet) and doesn't fit the generic engine's per-user model cleanly.
Response body = raw org.DisbursementResult struct (ref_code-keyed)Wrap in a generic {transaction_id, status} envelope as the original ask suggestedEvery other transaction-creation endpoint in this codebase (P2P transfer, topup, engine request) keys its response on ref_code, not a numeric/UUID transaction id — matching that idiom keeps the wire contract consistent. The mobile client's OrgDisbursementResult type was already written against this exact shape.
Idempotency key sourced from c.GetString("idempotency_key") (header, via middleware), request body has no idempotency fieldAccept idempotency key in JSON body like engineRequestReq.IdempotencyMatches the /v1/me/transactions/request + topup + transfer convention exactly (header-only). Mobile's useDisburseOrgMoney already sends it as a header.
New handler method on existing OrgHandler, not a new handler typeSeparate OrgTransactionHandlerOrgHandler already owns org-scoped mutations (Create, AddMember, CreatePolicy); one more org-scoped mutation keeps related code together, consistent with how the file is organized today.
