2. Main flow — request → pay (2 giai đoạn theo doc 04 §2.1)

sequenceDiagram
  autonumber
  actor A as Requester
  actor B as Payer
  participant API as API /v1/money-requests
  participant SVC as moneyrequest.Service
  participant DB as PostgreSQL
  participant ENG as workflow.Engine (P2P)
  A->>API: POST /money-requests {payer_phone, amount, note}
  API->>DB: INSERT money_requests(status=pending, expires_at=+72h)
  Note over B,API: 72h sau, B mở inbox
  B->>API: GET /money-requests/inbox
  B->>API: POST /money-requests/{id}/pay (Idempotency-Key)
  API->>SVC: Pay(payerID, requestID)
  SVC->>DB: BEGIN tx: SELECT money_requests FOR UPDATE
  alt status != pending HOẶC expires_at <= now()
    SVC-->>API: ERR_REQUEST_EXPIRED / ERR_REQUEST_NOT_PAYABLE (E19)
  else còn hiệu lực
    SVC->>DB: INSERT transactions(type=p2p, sender=B, receiver=A)
    SVC->>ENG: engine.Start(tx, "p2p_transfer", txnID) — CÙNG tx
    SVC->>DB: UPDATE money_requests SET status=paid, paid_txn_id\nWHERE id=$1 AND status=pending — COMMIT
  end
  Note over ENG,DB: Từ đây P2P chạy y hệt F5:\nVALIDATE→FRAUD_CHECK→MOVE_FUNDS→CONFIRM (async, poll timeline)

5. Decisions & trade-offs

Quyết địnhPhương án khácVì sao
E19 chặn bằng transaction boundary: SELECT ... FOR UPDATE + check expires_at > now() ngay trong Go, không đợi sweeper set status='expired' trướcChỉ dựa WHERE status='pending', để sweeper là nguồn duy nhất set expiredDeadline là một hàm của thời gian, không phải một trạng thái phải chờ cron gán nhãn — check trực tiếp expires_at loại bỏ toàn bộ cửa sổ race giữa "đã hết hạn về mặt logic" và "sweeper đã kịp đánh dấu"; sweeper chỉ dọn dẹp phần còn sót khi không ai bấm pay
Pay() nhân bản logic tạo P2P transaction thay vì gọi transfer.Service.Transfer()Sửa Transfer() nhận thêm tham số tx tùy chọnTransfer() tự quản lý tx của nó (Begin/Commit nội bộ) — để giữ khóa money_requests FOR UPDATE xuyên suốt cho tới khi transaction P2P + paid_txn_id commit cùng lúc, cách rẻ nhất là inline logic tương tự (đã có tiền lệ ở org.Service.CreateDisbursement làm y hệt với F5's pattern) thay vì thay đổi API công khai của module khác chỉ để phục vụ 1 caller
Split Bill chia đều dùng largest-remainder (BIGINT thuần), không chia rồi làm tròn từng phần tử độc lậptotal/n rồi bù chênh lệch vào phần tử cuốiLargest-remainder phân phối phần dư đều hơn (không dồn hết lệch vào 1 người); vẫn là số nguyên thuần, tổng luôn khớp input tuyệt đối — test rounding xác nhận trực tiếp
paid_txn_id gắn ngay khi P2P transaction ĐƯỢC TẠO (status transaction có thể vẫn processing), không đợi P2P completedRequest chỉ chuyển paid khi P2P thực sự completed (cần thêm 1 bước nghe kết quả)Khớp đúng state diagram gốc doc 04 (§2.1: "payer trả qua engine P2P — gắn transaction_id"); tránh phải thêm 1 tầng lắng nghe event mới chỉ để đồng bộ 2 state machine — nếu P2P sau đó fail (hiếm), UI vẫn đọc được trạng thái thật qua paid_txn_id → timeline API (đã có từ F5), không cần trường thứ hai để nói dối trạng thái tiền

6. Invariants touched (index.html §8)

Bất biếnF7 giữ bằng cách
Mọi đổi số dư qua ledger.PostPay() không đụng ledger — chỉ tạo transaction rồi giao thẳng cho engine.Start, tiền vẫn đi qua đúng MOVE_FUNDS handler F5
Idempotency-Key trên API tạo giao dịchPOST /money-requests/{id}/pay bắt buộc header, dùng làm idempotency_key của transaction P2P bên dưới — double-tap trả tiền không tạo 2 giao dịch (E01 pattern nguyên vẹn)
State transition luôn có guard WHERE statusFinalizeGuarded/DeclineGuarded/CancelGuarded đều WHERE status='pending'; Pay() còn cộng thêm AND expires_at > now() (E19)
AuthZ hai lớpPay/Decline chỉ payer đúng row; Cancel chỉ requester; predicate nằm trong SQL (WHERE id=$1 AND payer_id=$2), không chỉ kiểm tra ở handler
Điểm phỏng vấn của phase này: Request Money không phải là một luồng tiền mới — nó chứng minh workflow engine + ledger đã build từ F3-F5 đủ tổng quát để "mượn" nguyên vẹn cho một use case UX khác hẳn (xin tiền thay vì chuyển tiền chủ động), chỉ cần một lớp state mỏng phía trước. Đường đua thật của E19 là ranh giới transaction, không phải một cờ boolean.
