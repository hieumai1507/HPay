2. Main flow — org disbursement 2-tier end-to-end

sequenceDiagram
  autonumber
  actor MK as Maker
  actor C1 as Checker L1
  participant API as API /v1/org
  participant ENG as Engine
  participant APR as approval.Service
  participant DB as PostgreSQL
  participant OB as Outbox→Streams
  participant W as Worker handlers
  MK->>API: POST /org/{id}/transactions (Idempotency-Key)
  API->>DB: kiểm role maker + policy match (fail-fast ERR_NO_POLICY)
  API->>DB: tx: INSERT transactions(org_disbursement) + engine.Start
  Note over ENG,DB: VALIDATE → FRAUD_CHECK chạy auto (F5)
  ENG->>APR: advance gặp WAIT_APPROVAL → PauseHook (CÙNG DB tx)
  APR->>DB: match policy → INSERT approval_requests(snapshot tiers)\n+ txn → pending_approval (guarded)\n+ instance → waiting_approval
  C1->>API: GET /org/approvals?status=pending (My Tasks)
  C1->>API: POST /org/approvals/{id}/challenge
  API->>APR: eligibility (org? checker? level? chưa act? pending?)
  APR-->>C1: OTP (dev: trả code; prod: gửi kênh ngoài)
  C1->>API: POST /org/approvals/{id}/decide {approve, otp}
  API->>APR: verify OTP → tx: SELECT request FOR UPDATE
  APR->>DB: INSERT approval_actions (UNIQUE chặn double-act, E08)\nEvaluate(snapshot, actions)
  alt còn tier tiếp (L2 chưa ký)
    APR->>DB: current_level = 2 — request vẫn pending
  else đủ chữ ký
    APR->>DB: request → approved + finalized_at\n+ step_execution(WAIT_APPROVAL, completed)\n+ outbox ResultEvent{step: WAIT_APPROVAL, OK}\n+ audit_log — commit
    OB->>ENG: wf:events → OnResult (guard nới: waiting_approval + human step)
    ENG->>W: advance → MOVE_FUNDS → CONFIRM
    W->>DB: ledger.Post từ ví org → txn completed
  end
  alt reject
    APR->>DB: request → rejected + ResultEvent{OK:false}\n→ instance failed + txn failed (guarded), KHÔNG bút toán
  else quá 24h (sweeper)
    APR->>DB: claim-lease UPDATE…RETURNING → expired\n→ ResultEvent{OK:false} → fail sạch (E10)
  end

5. Decisions & trade-offs

Quyết địnhPhương án khácVì sao
Resume bằng ResultEvent chuẩn cho step WAIT_APPROVAL (nới guard OnResult chấp nhận waiting_approval khi step là human)Event type mới approval.finalized + consumer riêng (docs 00 §4.3)Tái dùng toàn bộ đường ống F4 (outbox → wf:events → OnResult, idempotent E06 sẵn); ít code hơn, không thêm consumer group. Ghi step_execution cho WAIT_APPROVAL nên timeline trọn vẹn. Semantics tương đương docs — sẽ note vào docs 00 sau merge
PauseHook interface trong package workflow, approval implement, inject ở mainEngine import approval trực tiếpTránh vòng import (approval đã import workflow types); engine vẫn không biết nghiệp vụ approval — đúng ranh giới module
Hook + tạo request chạy trong cùng DB tx với AdvanceInstance(waiting_approval)Tạo request async sau khi treoKhông tồn tại khoảnh khắc "instance treo mà chưa có request" — sweeper stuck không nhặt nhầm, checker không thấy thiếu
Finalize + outbox event + audit trong 1 tx FOR UPDATE, UNIQUE(request_id, checker_id) chặn double-actOptimistic + retryĐúng E08 theo cách DEH đã chứng minh (docs 00 §5.2); tranh chấp hiếm nên FOR UPDATE rẻ
Executor registry theo subject_type; F6 chỉ đăng ký org_transaction (= resume workflow)Switch-case cứngF9 thêm reversal/account_lock/policy_change bằng cách đăng ký executor — không sửa core approval
GetOwnerStatusByWalletID generic (user ∪ org)Nhánh if theo owner_type ở từng handlerSửa 1 chỗ ở tầng query; handler giữ nguyên logic "owner phải active" — org suspended giữa chừng fail giống E12

6. Invariants touched (index.html §8)

Bất biếnF6 giữ bằng cách
Mọi đổi số dư qua ledger.PostOrg disbursement đi đúng MOVE_FUNDS handler F5; approval module KHÔNG chạm ledger — chỉ phát event resume
State transition luôn có guard WHERE statusPendTransactionGuarded (processing→pending_approval), finalize request WHERE status='pending', OnResult guard theo (status, current_step); không UPDATE status trần
Event chỉ phát qua outboxResultEvent finalize/expire ghi outbox trong cùng tx quyết định — không XADD trực tiếp
Retry không tạo hiệu ứng đôiDuplicate finalize event bị OnResult guard nuốt (E06); UNIQUE(request_id, checker_id) chặn double-act (E08); org topup + disbursement dùng Idempotency-Key (E01 pattern)
Quyền nằm trong state machine, không if-else bypassMOVE_FUNDS chỉ chạy được khi engine advance qua WAIT_APPROVAL hợp lệ; event resume chỉ sinh từ finalize tx của approval module — không có cờ bypass (sửa điểm yếu DEH, docs 00 §5.3)
OTP hash, không plaintext; không log secretTái dùng nguyên OTP service F2 (hash bind challenge id, TTL 120s, max 3 — E11 đã test); decide không log code
Điểm phỏng vấn của phase này: cùng một engine chạy luồng tự động (P2P) lẫn luồng human-in-the-loop (org) — khác nhau đúng 1 dòng trong definition JSONB; và policy snapshot + FOR UPDATE + UNIQUE là bộ ba chống mọi race maker-checker (E08/E09) mà không cần distributed lock.
