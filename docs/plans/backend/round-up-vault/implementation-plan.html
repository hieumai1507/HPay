Implementation Plan — Round-up Vault Step

Feature slug: round-up-vault · Phase: C follow-up (deferred from vaults-engine) · Nguồn: doc 04 §2.2: "round-up — mỗi giao dịch chi lẻ tự bỏ phần làm tròn vào vault (thêm 1 step ROUND_UP optional trong definition)". Đánh dấu stretch/P2 — mục tiêu chính là khoe engine cấu hình được qua workflow definition, không phải một sản phẩm tiết kiệm đầy đủ.

2. Scope & Non-goals

Ships

  • Cột wallets.round_up_target BOOLEAN — mỗi user tối đa 1 vault nhận round-up tại một thời điểm (partial unique index).
  • API để user chọn/bỏ chọn vault làm round-up target.
  • Step handler round_up: sau CONFIRM của p2p_transfer, tính phần dư làm tròn của txn.Amount lên bội số cấu hình (mặc định 10.000 VND), và nếu user có round-up target + đủ số dư thì post thêm 1 cặp bút toán main→vault. Mọi điều kiện không thoả (không bật, không đủ tiền, chia hết) đều bỏ qua êm — không bao giờ làm giao dịch chính fail.
  • workflow_definitions.p2p_transfer version 2 (version 1 tắt is_active) thêm bước ROUND_UP.
  • Mobile: toggle "Làm hũ nhận làm tròn" trong màn Vault detail đã có.

Non-goals (defer)

  • Áp dụng round-up cho các service khác ngoài P2P_TRANSFER (MONEY_REQUEST, ORG_DISBURSEMENT...).
  • Đơn vị làm tròn tuỳ biến theo user — dùng 1 hằng số toàn hệ thống (env-configurable), không có UI chọn 1.000/10.000/50.000.
  • Nối lại gap có sẵn của ActionPipeline chưa được wire vào workflow definition nào — ghi nhận, không sửa trong plan này.

4. Schema changes

-- 000009_round_up_vault.up.sql
ALTER TABLE wallets ADD COLUMN round_up_target BOOLEAN NOT NULL DEFAULT false;

CREATE UNIQUE INDEX idx_wallet_round_up_target_unique
  ON wallets (owner_type, owner_id, currency)
  WHERE round_up_target AND purpose = 'vault';

UPDATE workflow_definitions SET is_active = false WHERE name = 'p2p_transfer' AND version = 1;

INSERT INTO workflow_definitions (name, version, steps, is_active) VALUES (
  'p2p_transfer', 2, '[
    {"name":"VALIDATE","type":"auto","handler":"validator","retry":3,"timeout_ms":5000,"on_failure":"fail"},
    {"name":"FRAUD_CHECK","type":"auto","handler":"fraud","retry":2,"timeout_ms":10000,"on_failure":"fail"},
    {"name":"MOVE_FUNDS","type":"auto","handler":"wallet","retry":3,"timeout_ms":5000,"on_failure":"compensate","config":{"compensatable":true}},
    {"name":"CONFIRM","type":"auto","handler":"confirmer","retry":3,"timeout_ms":5000,"on_failure":"fail"},
    {"name":"ROUND_UP","type":"auto","handler":"round_up","retry":3,"timeout_ms":5000,"on_failure":"fail"}
  ]'::jsonb, true
);

Theo đúng convention gen-migration: version tăng dần trên cùng name, không sửa tại chỗ v1 (đang chạy cho các instance cũ dở dang vẫn tham chiếu đúng definition_id của v1).

5. API changes

PATCH /v1/vaults/{id}/round-up-target
  Body: {"enabled": true}
  200: {"id","label","round_up_target": true}
  404: ERR_VAULT_NOT_FOUND (không sở hữu / không tồn tại)

Không thêm endpoint tiền — round-up không phải một giao dịch user khởi tạo, nó là hệ quả tự động của MOVE_FUNDS trong p2p_transfer.

7. Rollout & risk

  • Feature flag: không cần — mặc định user chưa bật round-up target thì step luôn no-op, an toàn để merge thẳng.
  • Backfill: không cần, cột mới mặc định false.
  • Rủi ro đã biết: nếu round_up handler lỗi hạ tầng hết số lần retry, failInstance vẫn set workflow_instances.status='failed' ở bước ROUND_UP dù transactions.status đã completed từ trước (do FailTransactionGuarded guard). Timeline mobile sẽ hiện instance "failed" ở bước cuối dù tiền đã chuyển xong — chấp nhận vì đây là bước không bắt buộc và rủi ro thấp (chỉ lỗi hạ tầng thật sự mới rơi vào nhánh này). Không sửa failInstance trong plan này vì ảnh hưởng mọi step cuối của mọi definition.
  • Rollback: tắt is_active của v2, bật lại v1 — instance mới sẽ không có ROUND_UP; instance đang chạy dở của v2 (hiếm, workflow ngắn) tự hoàn tất bình thường.
