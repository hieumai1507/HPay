Solution Architecture — Round-up Vault Step

Song hành với implementation-plan.html. Nguyên tắc chủ đạo: round-up là một step thêm vào cuối workflow definition, không phải một tính năng tách rời — đúng tinh thần "khoe engine cấu hình được" của doc 04 §2.2.

1. Context

flowchart LR
  mob["📱 Vault detail\ntoggle round-up"] --> VAPI["PATCH /v1/vaults/{id}/round-up-target"]
  VAPI --> DB1[("wallets\nround_up_target")]
  P2P["📱 P2P transfer confirm"] --> ENG["🔀 Workflow Engine\ndef p2p_transfer v2"]
  ENG --> VALIDATE --> FRAUD --> MOVE["MOVE_FUNDS\n(wallet handler)"] --> CONFIRM --> RU["ROUND_UP\n(round_up handler, mới)"]
  RU --> DB1
  RU --> LE["⚖️ Ledger\n2 legs bổ sung: main → vault"]

2. Main flow — giao dịch P2P kèm round-up

sequenceDiagram
  participant U as User
  participant ENG as Engine
  participant RU as round_up handler
  participant Q as store.Queries
  participant L as Ledger

  U->>ENG: confirm P2P transfer 123.000đ
  ENG->>ENG: VALIDATE → FRAUD_CHECK → MOVE_FUNDS (123.000 + fee) → CONFIRM
  ENG->>RU: dispatch ROUND_UP
  RU->>Q: GetTransactionByWorkflow(txnID)
  RU->>RU: diff = ceil(123.000/10.000)*10.000 - 123.000 = 7.000
  alt diff == 0 (chia hết)
    RU-->>ENG: OK {round_up_applied:false, reason:"exact"}
  end
  RU->>Q: GetRoundUpTargetVault(sender.ownerID)
  alt không có target
    RU-->>ENG: OK {round_up_applied:false, reason:"no_target"}
  end
  RU->>Q: GetWalletByID(main) — số dư sau MOVE_FUNDS
  alt số dư còn lại < diff
    RU-->>ENG: OK {round_up_applied:false, reason:"insufficient_balance"}
  end
  RU->>L: Post(txnID, [debit main 7.000, credit vault 7.000])
  L-->>RU: ok
  RU-->>ENG: OK {round_up_applied:true, amount:7.000}
  ENG-->>U: instance completed

Bất biến thiết kế: mọi nhánh "không áp dụng" trả OK, không bao giờ trả lỗi terminal cho lý do nghiệp vụ — round-up là best-effort, không được phép làm hỏng trạng thái completed của giao dịch chính đã xong ở bước CONFIRM trước đó.

3. State — nhánh quyết định của round_up handler

stateDiagram-v2
  [*] --> ComputeDiff
  ComputeDiff --> Skipped: diff == 0 (chia hết đơn vị)
  ComputeDiff --> LookupTarget: diff > 0
  LookupTarget --> Skipped: không có round_up_target
  LookupTarget --> CheckBalance: có target
  CheckBalance --> Skipped: main wallet không đủ diff
  CheckBalance --> Posted: đủ số dư
  Posted --> [*]
  Skipped --> [*]

4. Data model delta

erDiagram
  wallets ||--o{ ledger_entries : journals

    boolean round_up_target "NEW, mặc định false"

  }
  workflow_definitions {
    string name "p2p_transfer"
    int version "2, NEW — v1 tắt is_active"

Ràng buộc: partial unique index (owner_type, owner_id, currency) WHERE round_up_target AND purpose='vault' — đảm bảo tại một thời điểm mỗi user chỉ có tối đa 1 vault nhận round-up; đổi target là một transaction DB (unset cũ, set mới) để không vi phạm index giữa chừng.

5. Decisions & trade-offs

Quyết địnhPhương án khácVì sao
Thêm version 2 của p2p_transfer, không sửa v1 tại chỗUPDATE steps của v1Instance đang chạy dở tham chiếu definition_id cố định; sửa JSONB tại chỗ sẽ làm ParseSteps đọc definition khác với lúc Start — vi phạm bất biến workflow (đã có convention version tăng dần trong migration 000003)
Round-up không bao giờ fail transaction chínhCoi round-up là bước bắt buộc như MOVE_FUNDSDoc 04 gọi đây là stretch/optional; ép buộc sẽ biến một tính năng phụ thành single point of failure cho toàn bộ P2P
Đơn vị làm tròn là hằng số hệ thống (env, mặc định 10.000)Cấu hình theo userGiữ phạm vi nhỏ đúng "stretch"; thêm UI chọn đơn vị là một tính năng khác, không nằm trong doc 04
Vault target xác định qua cột round_up_target trên chính walletsBảng cấu hình riêng user_preferencesVault đã là 1 dòng wallets; thêm cờ ngay trên đó tránh 1 bảng chỉ để lưu 1 quan hệ 1-1
Không đụng gap ActionPipeline chưa được wireNhân tiện wire luôn action_pipeline vào definitionNgoài phạm vi round-up; wire sai chỗ có thể kích hoạt các "Directional Integration" actions (gọi gateway ngân hàng thật) ngoài ý muốn — cần plan riêng để review kỹ
