1.Kiến trúc tổng thể

Modular monolith 1 binary Go — các module giao tiếp qua Redis Streams (consumer group + XACK, không phải Pub/Sub thường) và transactional outbox, nên tách được thành service riêng bất cứ lúc nào mà không đổi contract.

4.Workflow Engine — luồng P2P chuẩn

Mỗi loại giao dịch là một workflow definition (JSONB, version hóa) — thêm luồng mới bằng INSERT, không sửa code. Step auto chạy qua handler; step human_approval treo instance chờ người duyệt.

sequenceDiagram
  autonumber
  actor U as User
  participant API as API (Gin)
  participant DB as PostgreSQL
  participant OB as Outbox relay
  participant RS as Redis Streams
  participant W as Worker (handlers)
  U->>API: POST /v1/transactions/transfer (Idempotency-Key)
  API->>DB: tx: transactions + workflow_instance + outbox↳step.start
  API-->>U: 202 {refCode} — app chuyển màn Processing (poll)
  OB->>RS: XADD wf:steps:validator
  RS->>W: VALIDATE → ok → outbox↳completed
  RS->>W: FRAUD_CHECK → score<40 safe
  RS->>W: DEBIT — SELECT FOR UPDATE (sort id) → ledger 2 bút toán
  RS->>W: CREDIT — idempotent theo attempt
  RS->>W: CONFIRM → txn=completed → notify 2 chiều
  Note over W,DB: fail giữa chừng? → saga compensation:\npost bút toán đảo, KHÔNG xóa ledger

5.Maker-Checker & Approval engine (hạ tầng dùng chung)

Không chỉ cho lệnh chi doanh nghiệp — mọi thao tác nhạy cảm của admin (reversal, khóa tài khoản, đổi policy/fee) cũng đi qua cùng một approval engine: Maker ≠ Checker, policy snapshot chống race, chữ ký OTP, audit đầy đủ.

flowchart LR
  mk["👤 Maker\n(org maker / admin CS)"] --> rq["approval_requests\nsubject: org_txn | reversal |\naccount_lock | policy_change\n+ policy_snapshot"]
  rq --> ib["📥 Inbox checker / My Tasks admin"]
  ib --> d{"Checker ký OTP\nFOR UPDATE + unique(1 người 1 lần)"}
  d -->|"đủ chữ ký theo tier"| ex["▶️ Thực thi:\nresume workflow / đảo bút toán /\nkhóa TK / áp policy mới"]
  d -->|"reject"| rj["❌ Từ chối + lý do"]
  d -->|"quá 24h"| xp["⏰ Expired — fail sạch"]
  ex & rj & xp --> au["📜 audit_logs (immutable)"]
Khác biệt so với hệ tham khảo: không có cờ "bypass auth" sau khi duyệt — bước tài chính chỉ chạy được khi state machine đi qua WAIT_APPROVAL hợp lệ. Quyền nằm trong cấu trúc state, không phải if-else.

7.Vòng đời trạng thái giao dịch

stateDiagram-v2
  [*] --> created : API nhận (idempotency ok)
  created --> pending_approval : gặp step human_approval
  created --> processing : workflow chạy
  pending_approval --> processing : đủ chữ ký
  pending_approval --> failed : reject / hết hạn 24h
  processing --> completed : CONFIRM ok — GL đã cân
  processing --> processing_async : bên phụ thuộc chậm\n(recoverable, không phải lỗi)
  processing_async --> completed : recovery job replay ok
  processing_async --> failed : recovery hết lượt
  processing --> failed : lỗi + saga bồi hoàn xong
  completed --> reversed : reversal qua maker-checker\n(bút toán đảo, không xóa)
  completed --> [*]
  failed --> [*]
  reversed --> [*]
Bất biến: sau completed trạng thái không bao giờ sửa tại chỗ. Hoàn tiền = giao dịch đảo mới có reversal_of trỏ về gốc.

8.Tiền & Sổ cái — các bất biến

Bất biếnĐược đảm bảo bởi
Tiền là BIGINT đơn vị nhỏ nhất — không bao giờ floatSchema + skill fintech-review chặn từ CI
Mỗi giao dịch ≥ 2 bút toán, tổng Nợ = tổng CóLedger service + test invariant + recon nội bộ
wallets.balance = SUM(ledger_entries) của víRecon nội bộ hằng ngày đối chiếu
Ledger chỉ INSERT — không UPDATE/DELETETrigger + quyền DB + review
Retry không tạo giao dịch đôiIdempotency-Key unique + attempt check trong handler
Event không phát trước commit, không mất sau commitTransactional outbox + Streams XACK/XAUTOCLAIM
Không deadlock khi 2 ví chuyển chéoLock ordering theo wallet_id tăng dần
Biometric chỉ mở khóa app — chuyển tiền luôn cần PIN/OTPAuth matrix client + server

9.KYC · Fraud · Đối soát

🪪 KYC

Chụp CCCD + selfie → Claude vision trả {score, reasons} → ≥85 auto-approve · 50–85 vào queue người duyệt (kèm giải thích AI) · <50 reject. Chạy như một workflow definition riêng — tái dùng retry/timeout/log.

🚨 Fraud

Rule deterministic trước (velocity, amount spike, new device, giờ lạ) → vùng xám 40–70 mới hỏi LLM tổng hợp + giải thích tiếng Việt. LLM không bao giờ tự quyết chặn tiền — quyết định cứng là rule + con người.

⚖️ Đối soát

Cron 00:15: so khớp theo ref_code với sao kê mock → matched / mismatch / missing từng chiều → AI tóm tắt nguyên nhân lệch → export Excel. Kèm recon nội bộ: SUM ledger = balance từng ví.

🔄 Recovery

Job 5 phút/lần quét instance kẹt (running/compensating quá ngưỡng) → replay step hiện tại (handler idempotent). Giao dịch "lơ lửng" không bao giờ bị quên.

11.Ma trận edge case (bắt buộc có test)

37 case được liệt kê và gắn test: E01–E20 backend (double-spend, deadlock chéo, worker chết giữa saga, event trùng, checker race, policy đổi giữa chừng, Redis sập…), M01–M12 mobile (double-tap, timeout không báo fail vội, refresh token single-flight, BigInt tiền…), A01–A07 admin (409 conflict giữa 2 reviewer, cursor pagination chống trôi hàng…). CI đếm test theo danh sách — thiếu là fail build. Chi tiết trong doc 01/02/03.
