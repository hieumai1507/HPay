# Create a mobile TanStack Query hook

> Trigger: Create a TanStack Query hook (query or mutation) for a domain feature in hpay-mobile, wired to the generated API client. Trigger when the user asks to "add a hook for X endpoint", "wire up the Y API", or a screen needs data that has no hook yet.

# gen-feature-hook — Query/mutation hook backed by the generated contract

## Project conventions (MUST follow)

- One folder per domain: `src/features/<domain>/` (e.g. `wallet`, `transfer`,
  `kyc`, `approval`, `money-request`). Hooks live in `src/features/<domain>/hooks.ts`
  (or split per hook if the file grows).
- Never hand-write request/response types. Import from the generated
  `src/api/schema.d.ts` (`components['schemas']['X']`, `paths['/v1/...']['get']`).
  If a type is missing or wrong, the fix is `npm run gen:api` after the backend's
  `openapi.yaml` changes — never patch the generated file, never redeclare the shape by hand.
- All requests go through `apiRequest<T>` from `src/api/client.ts`. It already
  attaches `Authorization`, `X-Device-Id`, `X-Request-Id`, and handles the
  401 → single-flight-refresh → retry-once dance (M04) — do not reimplement any of that.
- **Queries** (GET): wrap in `useQuery`. Give them a real `queryKey` array
  (`['wallets']`, `['transactions', cursor]`) — no magic strings duplicated across files.
- **Mutations that move money** (POST transfer/topup/pay/decide/etc.):
  - MUST accept/generate an `Idempotency-Key` and pass `idempotencyKey` in the
    `apiRequest` call. The key is generated by the calling screen via
    `useIdempotencyKey`, not inside the hook — the hook just threads it through.
  - MUST NOT set `retry` — mutations default to `retry: false` at the QueryClient
    level (`src/api/query-client.ts`) specifically so a hook can't silently
    double-fire a money-moving request. Don't override it per-mutation.
  - On success, invalidate the queries it affects (e.g. a transfer invalidates
    `['wallets']` and `['transactions']`) via `queryClient.invalidateQueries`.
- Errors: let `ApiError`/`NetworkError` (from `src/lib/errors.ts`) propagate out of
  the hook unchanged. Screens call `describeError(err)` for display — hooks never
  format user-facing strings.
- Async (202-accepted) endpoints: the hook that kicks off the action returns the
  initial response; a *separate* hook (or the screen directly) uses
  `PollingTransactionWatcher` from `src/lib/polling.ts` against the
  `/transactions/{refCode}/timeline` endpoint to track completion. Don't poll inside
  the mutation's `onSuccess`.

## Steps

1. Confirm the endpoint exists in `hpay-backend/api/openapi.yaml`. If not,
   STOP — propose the backend change first (contract-first).
2. `npm run gen:api` if the schema was just updated, then check the generated types
   under `src/api/schema.d.ts` for the exact request/response shape.
3. Write the hook in `src/features/<domain>/hooks.ts`:
   ```ts
   export function useTransferMutation() {
     return useMutation({
       mutationFn: (input: TransferInput & { idempotencyKey: string }) =>
         apiRequest<TransferResponse>('/v1/transactions/transfer', {
           method: 'POST',
           body: input,
           idempotencyKey: input.idempotencyKey,
         }),
     });
   }
   ```
4. Add a unit test mocking `apiRequest` (or `global.fetch`, see
   `src/api/__tests__/refresh.test.ts` for the fetch-mocking pattern) covering the
   happy path and at least one `ERR_*` failure mapped through `ApiError`.
5. Run `npm run typecheck && npm run lint && npm test`.

## Checklist before finishing

- [ ] No hand-written request/response type — everything from `schema.d.ts`
- [ ] Money-moving mutation threads an `idempotencyKey` through to `apiRequest`
- [ ] No `retry` override on a mutation
- [ ] Affected queries invalidated on mutation success
- [ ] Hook returns raw errors; no message formatting inside `src/features/`
