Engineering

How it stays correct when things go wrong

A payment system is judged by its failures: a retry, a crash between two writes, two requests at once. This page shows the design and the decisions behind it. Every claim links to a record in the repository.

Architecture

One API, one database, a queue for the slow parts

The API writes the payment and an outbox event in the same database transaction. A relay moves outbox events to Redis Streams. Workers run the steps of the payment and write the ledger.

Fact check: the relay, streams, workers and recovery are in internal/outbox and internal/workflow (recovery.go reclaims stream messages with XAUTOCLAIM and sweeps stuck instances in the database).

Decisions

The choices that matter for money

Each one has a written record with the options considered. Four of them are shown here in full shape: the problem, the choice, and what it cost.

Idempotency keys belong to a user and to one request ADR-0011 · BUG-0002

Problem

The key was unique across all users and not tied to what was asked. Another user's key, or the same key with a different amount, returned someone else's or a stale result.

Choice

Unique on (user, key) plus a hash of the request on the transaction row. Same key and same request returns the first result. Same key and a different request is a 409. A missing key is rejected.

Alternatives rejected

A separate keys table (two writes that must stay in step), Redis-only keys (not a source of truth, unsafe if evicted), and a hash alone (the cross-user leak stays).

Cost

Keys live as long as transactions. A client that sends a fresh key on every retry is not deduplicated.

Daily limits hold under parallel requests BUG-0017 · BUG-0021

What happened

A request waits for its PIN and does not count toward the quota. Five held requests of 1,500,000 each all passed the check against a 2,500,000 daily limit, and all five started when confirmed in parallel.

Fix

Re-check the limits when a held request is confirmed, inside the transaction that starts the workflow, under a per-user advisory lock. Volume is counted from when money started to move, in a fixed UTC+7 window.

Proof

A red test that reproduced the five-of-five result, then a regression test that runs the confirms in parallel under -race.

Related

The same flaw was found later in the pay path of money requests (BUG-0021) and fixed the same way.

The ledger cannot post the same payment twice ADR-0010 · BUG-0001

Problem

Workers can receive the same step twice after a crash or a redelivery. A step that posts to the ledger then posted the same payment twice (BUG-0001).

Choice

A guard row per payment and kind of posting is inserted in the same database transaction as the entries. A duplicate is recognised and the step completes as already done.

Locking

Every wallet a posting touches is locked in one ORDER BY id ... FOR NO KEY UPDATE statement, so two transfers in opposite directions cannot wait on each other. The weaker lock is needed because inserting a transaction row takes a shared lock on its wallets.

Check

After every load test, each wallet balance is compared with the sum of its ledger lines.

PIN hashing with a server-side pepper ADR-0018

Problem

A PIN has few possible values, so a leaked database could be cracked offline whatever the hash. The old setting was also so heavy that it limited how many payments could be accepted per second.

Choice

Mix the PIN with a secret held outside the database (HMAC), then hash with argon2id at the OWASP minimum cost. The hash records which secret was used, so the secret can be rotated. Old hashes still verify and are rewritten on the next correct entry.

Result

In one load run on a laptop, accepted payments per second rose from 8.9 to 34.5. End-to-end time got worse, from 43.7 s to 67.2 s at the median, because the workflow became the next limit.

Honest note

One run per column, large run-to-run noise. Treat it as a direction. A rotation drill has not been done.
