How a change is made

Work follows a fixed path, written as skills in the repository: clarify, write the spec, plan, design test cases, write failing tests first, implement, verify every case, review, then update the documentation. A bug fix first searches the bug ledger, then records itself there.

Red tests first

A test must fail for the right reason before the fix. Mutation checks then confirm the tests catch a deliberately broken version.

Bugs leave a record

15 records with symptom, root cause, other places with the same flaw, fix and regression test.

Reviews are independent

Code, security and test reviewers run separately and their findings are merged. A change that touches money, locking or the workflow also needs before and after load numbers.

Docs change with code

Domain rules, architecture pages, API and error references, and the user guide are updated in the same change.
